# 데이터 계약과 스키마 진화

데이터 파이프라인 장애의 상당수는 코드 버그가 아니라 **업스트림의 조용한 변경**에서 시작된다. 서비스 팀이 컬럼 이름을 바꾸거나, 정수였던 필드에 문자열을 넣기 시작하거나, 이벤트 하나를 더 이상 보내지 않게 되었을 때, 이를 소비하는 피처 파이프라인·학습 데이터·대시보드는 오류 없이 잘못된 결과를 내며 며칠 뒤에야 발견된다. 책 5.3(데이터 거버넌스)과 6.1.4(데이터 일관성 및 무결성 유지 전략), 8장(데이터 처리 파이프라인)은 이 문제의 배경을 다룬다. 이 문서는 그 해법으로 자리 잡은 **데이터 계약(data contract)** 과, 계약이 있어도 피할 수 없는 변경을 다루는 **스키마 진화(schema evolution)** 전략을 정리한다.

<br>

## 1. 데이터 계약이란

데이터 계약은 데이터를 생산하는 쪽과 소비하는 쪽이 합의한, **기계가 검증할 수 있는 명세**다. API 명세(OpenAPI)가 서비스 간 인터페이스를 고정하는 것처럼, 데이터 계약은 테이블·이벤트·파일의 인터페이스를 고정한다. 문서로만 존재하는 "데이터 사전"과 다른 점은 계약이 파이프라인 안에서 자동으로 검증되고, 위반 시 배포나 적재를 막는다는 것이다.

계약에 담기는 내용은 다음과 같다.

| 구성 요소 | 내용 | 예 |
| --- | --- | --- |
| **스키마** | 필드 이름, 타입, null 허용 여부, 중첩 구조 | `order_id: string, not null` |
| **의미(semantics)** | 필드의 정의, 단위, 열거값의 의미 | `amount`는 세금 포함, KRW, 원 단위 정수 |
| **품질 규칙** | 값의 범위, 유일성, 참조 무결성, 허용 null 비율 | `amount >= 0`, `order_id` 유일, `user_id` null 비율 < 0.1% |
| **SLA** | 갱신 주기, 지연 허용치, 가용성 | 매일 06:00 KST까지 전일 데이터 적재 완료 |
| **소유권** | 생산 팀, 담당자, 연락 채널 | 주문 플랫폼팀, #data-orders |
| **버전과 변경 정책** | 현재 버전, 호환성 보장 범위, 폐기(deprecation) 절차 | v2.1, 하위 호환 변경만 무통보 허용, 파괴적 변경은 60일 전 공지 |
| **민감도 분류** | 개인정보·비밀 등급, 마스킹 규칙 | `phone`은 PII, 다운스트림에는 해시값만 제공 |

**계약을 어디에 두는가**

계약은 코드처럼 저장소에서 버전 관리한다. 형식은 YAML/JSON 기반의 명세 표준(Open Data Contract Standard 등), Protobuf/Avro 스키마 파일, dbt의 모델 계약(`contract: enforced`), 또는 자체 정의 형식을 쓴다. 중요한 것은 형식보다 **생산자 저장소에 계약이 있고, 생산자의 CI가 계약을 검증한다**는 배치다. 소비자 쪽에서만 검증하면 문제를 발견은 하되 막지는 못한다.

<br>

## 2. 계약 검증의 세 지점

```
[생산자 코드 변경]
   │
   ▼
① CI: 스키마 호환성 검사 ─ 파괴적 변경이면 병합 차단
   │
   ▼
[데이터 생성·발행]
   │
   ▼
② 적재 시점: 스키마·품질 규칙 검증 ─ 위반 데이터는 격리 테이블로
   │
   ▼
[저장소]
   │
   ▼
③ 읽기 시점: 기대 스키마 확인, 통계적 이상 탐지
   │
   ▼
[소비자 파이프라인] → 피처 / 학습 데이터 / 대시보드
```

- **배포 전(CI)**: 생산자가 스키마 파일이나 ORM 모델을 변경하면 CI가 현재 계약과 비교해 호환성 등급(하위 호환/파괴적)을 판정한다. 파괴적 변경은 계약 버전 상향과 소비자 승인 없이는 병합되지 않는다. 가장 저렴하게 문제를 막는 지점이다.
- **적재 시점(write-time)**: 실제 데이터가 계약을 만족하는지 검증한다. 스트리밍에서는 스키마 레지스트리가 발행 시점에 스키마를 강제하고, 배치에서는 적재 작업 안에서 품질 규칙(Great Expectations, Soda, dbt tests 등)을 실행한다. 위반 데이터는 격리 테이블(quarantine)로 보내고 정상 데이터만 적재하는 방식이 파이프라인 전체를 멈추는 것보다 실용적인 경우가 많다.
- **읽기 시점(read-time)**: 소비자가 자신이 기대하는 스키마를 명시하고 불일치 시 실패하게 한다. 생산자가 계약을 지키지 않는 레거시 소스에 대한 최후 방어선이며, 통계적 이상 탐지(행 수 급변, 분포 이동)도 이 지점에서 수행한다. 책 7.3.2의 데이터 드리프트 감지가 여기에 해당한다.

<br>

## 3. 스키마 진화: 호환성 규칙

계약이 있어도 스키마는 바뀌어야 한다. 문제는 변경 자체가 아니라 소비자가 준비되지 않은 변경이다. 변경을 호환성 관점에서 분류하면 다음과 같다.

| 변경 | 하위 호환(기존 소비자가 새 데이터를 읽을 수 있음) | 상위 호환(새 소비자가 기존 데이터를 읽을 수 있음) | 처리 방식 |
| --- | --- | --- | --- |
| 기본값 있는 필드 추가 | O | O | 무통보 가능 |
| 기본값 없는 필수 필드 추가 | O (기존 소비자는 무시) | X (기존 데이터에 값 없음) | 기본값 부여 또는 nullable로 추가 |
| 선택(optional) 필드 삭제 | X (해당 필드 참조 소비자 실패) | O | 폐기 공지 후 유예 기간 뒤 삭제 |
| 필드 이름 변경 | X | X | 새 필드 추가 → 이중 기록 → 구 필드 폐기 |
| 타입 변경(int → string) | X | X | 새 필드로 추가, 구 필드 유예 후 삭제 |
| 타입 확장(int → long) | 대체로 O | X | 포맷별 규칙 확인(Avro는 허용, Parquet 리더는 다를 수 있음) |
| 열거값 추가 | 소비자 구현에 따라 다름 | O | 소비자가 알 수 없는 값을 처리하도록 계약에 명시 |
| 의미 변경(단위, 정의) | 스키마상 O, 실질적으로 X | — | 가장 위험. 반드시 새 필드로 분리 |

마지막 행이 중요하다. `amount`의 단위를 원에서 천 원으로 바꾸는 변경은 스키마 검사를 모두 통과하지만 모든 다운스트림 계산을 망가뜨린다. **의미가 바뀌면 이름도 바꾼다**(`amount` → `amount_krw_thousand`)는 규칙이 이를 막는 유일한 방법이다.

**확장-축소(expand-contract) 패턴**

파괴적 변경은 한 번에 하지 않고 세 단계로 나눈다.

1. **확장(expand)**: 새 필드/새 테이블을 추가하고 구 필드와 함께 이중 기록(dual write)한다.
2. **이전(migrate)**: 소비자가 새 필드로 옮길 시간을 준다. 계약의 폐기 정책(예: 60일)이 이 기간을 규정한다. 구 필드 사용량을 쿼리 로그로 추적해 이전 진행률을 확인한다.
3. **축소(contract)**: 구 필드 사용이 0이 되면 삭제한다.

이 패턴은 책 7.2.3의 모델 버전 관리·롤백 전략과 같은 원리다. 모델과 데이터 모두 "새 것을 옆에 두고, 옮기고, 옛 것을 걷어낸다".

## 4. 스트리밍 환경: 스키마 레지스트리

Kafka 같은 스트리밍 플랫폼(책 8.3, 부록 A.9)에서는 메시지가 바이트 배열이므로 스키마 강제가 별도 장치 없이는 불가능하다. **스키마 레지스트리**는 토픽별 스키마를 중앙에서 버전 관리하고, 프로듀서가 발행할 때 호환성 규칙을 검사한다.

- **직렬화 포맷**: Avro, Protobuf, JSON Schema가 사용된다. Avro는 스키마 진화 규칙이 잘 정의되어 있고 압축 효율이 좋아 데이터 파이프라인에서 널리 쓰인다. Protobuf는 서비스 간 gRPC와 공유하기 좋다. JSON Schema는 가독성이 높지만 타입 진화 규칙이 느슨하다.
- **호환성 모드**: BACKWARD(새 스키마로 구 데이터 읽기 가능, 소비자 먼저 업그레이드), FORWARD(구 스키마로 새 데이터 읽기 가능, 프로듀서 먼저 업그레이드), FULL(양쪽 모두), NONE. 데이터 파이프라인에서는 소비자가 과거 데이터를 재처리해야 하는 경우가 많아 BACKWARD 또는 FULL을 기본으로 둔다.
- **스키마 ID 임베딩**: 메시지 앞에 스키마 ID를 붙여 소비자가 정확한 스키마로 역직렬화한다. 같은 토픽에 여러 버전이 공존해도 안전하게 읽을 수 있다.
- **레지스트리 자체의 거버넌스**: 누가 스키마를 등록·변경할 수 있는지 접근 제어를 두고, 변경은 코드 리뷰를 거친 CI에서만 수행하게 한다. 개발자가 콘솔에서 직접 스키마를 올리는 경로는 막는다.

## 5. 데이터 레이크·웨어하우스 환경

Parquet 파일이 쌓이는 데이터 레이크(책 6.2, 부록 B.5 레이크하우스)에서는 파일마다 스키마가 다를 수 있어 스키마 진화가 특히 까다롭다.

- **테이블 포맷의 스키마 진화 지원**: Apache Iceberg, Delta Lake, Apache Hudi는 테이블 수준 메타데이터로 스키마를 관리해 컬럼 추가·삭제·이름 변경·타입 확장을 안전하게 지원한다. 특히 Iceberg는 컬럼을 이름이 아닌 ID로 추적하므로 이름 변경이 기존 파일을 다시 쓰지 않고도 가능하다. 원시 Parquet 디렉터리 대신 이들 포맷을 쓰는 것 자체가 스키마 진화의 절반을 해결한다. 포맷과 카탈로그 선택은 [오픈 테이블 포맷과 카탈로그 표준](./open-table-formats-catalogs.md)에서 다룬다.
- **스키마 온 리드(schema-on-read)의 함정**: "일단 넣고 읽을 때 해석한다"는 접근은 유연하지만, 해석 로직이 소비자마다 흩어져 같은 데이터를 다르게 읽는 문제를 낳는다. 원시 계층(raw)에는 유연하게 적재하되, 정제 계층(curated)부터는 계약을 강제하는 것이 일반적인 절충이다.
- **파티션 진화**: 파티션 키 변경(일 → 시간 단위)은 스키마 변경 이상으로 파괴적이다. Iceberg의 숨은 파티셔닝(hidden partitioning)처럼 파티션 레이아웃을 쿼리와 분리하는 기능을 활용하거나, 새 테이블로 이전한다.
- **dbt 계약**: dbt를 사용한다면 모델에 `contract: enforced`를 선언해 컬럼 이름·타입을 빌드 시점에 강제하고, `versions`로 모델의 파괴적 변경을 v1/v2로 병존시킬 수 있다.

## 6. ML 파이프라인에서의 특수성

데이터 계약은 ML에서 두 가지 이유로 더 중요하다.

첫째, **학습-서빙 스큐(training-serving skew)** 다. 학습 시점의 피처 정의와 서빙 시점의 피처 정의가 어긋나면 모델은 오류 없이 나쁜 예측을 낸다. 피처 스토어(책 15.2.4)는 피처 정의를 한곳에 두어 이를 막으려는 장치이며, 피처 정의 자체가 곧 계약이다. 피처의 타입·범위·null 처리·계산 로직 버전을 계약에 명시하고, 서빙 시점에 입력이 학습 분포와 맞는지 검증한다.

둘째, **재현성**이다. 6개월 전 모델을 재학습하려면 그 시점의 스키마로 데이터를 읽어야 한다. 스키마 버전을 학습 메타데이터(MLflow 등)에 함께 기록하고, 테이블 포맷의 타임 트래블(time travel) 기능으로 당시 스냅샷을 읽을 수 있게 한다.

이를 위한 실무 규칙은 다음과 같다.

- 학습 데이터 생성 파이프라인의 입력 테이블은 모두 계약이 있는 정제 계층에서 읽는다. 원시 계층 직접 참조를 금지한다.
- 피처 파이프라인 시작 시 입력 스키마를 검증하고, 실패 시 이전 성공 버전의 피처를 유지하며 알림을 보낸다. 잘못된 피처로 모델을 갱신하는 것보다 하루 지연이 낫다.
- 모델 서빙 API의 입력 스키마도 계약으로 관리하고, 학습 시 사용한 피처 스키마와 자동으로 대조한다.

## 7. 도입 순서

계약을 모든 테이블에 한 번에 도입하려는 시도는 대개 실패한다. 다음 순서가 현실적이다.

1. **가장 비싼 장애를 낸 소스부터**: 지난 1년간 다운스트림 장애를 가장 많이 일으킨 테이블·토픽 3~5개를 고른다.
2. **현재 상태를 계약으로 문서화**: 실제 데이터를 프로파일링해 스키마·null 비율·값 범위를 추출하고, 생산 팀과 함께 의미와 SLA를 확인해 첫 계약을 작성한다.
3. **읽기 시점 검증부터 시작**: 소비자 파이프라인에 검증을 넣어 위반을 관측한다. 처음에는 실패시키지 않고 경고만 낸다.
4. **생산자 CI로 이동**: 위반 패턴이 파악되면 생산자 저장소에 계약과 호환성 검사를 넣는다. 이 단계가 조직적 합의를 요구하므로 가장 오래 걸린다.
5. **확장**: 계약 템플릿과 검증 라이브러리를 공통 도구로 만들어 새 소스에는 기본 적용되게 한다.

계약은 기술보다 조직의 문제다. "데이터를 만드는 팀이 그 데이터의 소비자에 대한 책임을 진다"는 원칙이 합의되지 않으면 어떤 도구도 작동하지 않는다. 책 5.3.1의 데이터 거버넌스 구성 요소에서 소유권(ownership)을 가장 먼저 다루는 이유가 여기에 있다.
