# 멀티모달 RAG

책 12.4가 다룬 RAG는 텍스트 문서를 전제로 한다. 그런데 실무 문서의 상당 부분은 텍스트만이 아니다. 제품 매뉴얼의 도해, 재무 보고서의 표와 차트, 계약서의 스캔 이미지, 상품 페이지의 사진, 강의 자료의 슬라이드. 텍스트만 추출해 임베딩하는 RAG는 이 정보를 잃거나 왜곡한다. 표는 셀 순서가 뒤섞인 텍스트 덩어리가 되고, 차트는 "그림 3"이라는 캡션만 남으며, 스캔 문서는 OCR 오류가 그대로 색인된다. 비전-언어 모델(VLM)의 발전으로 이 문제에 대한 실용적 해법이 자리 잡았다. 이 문서는 [RAG 품질 저하 요인과 대응 전략](./rag-quality-risks.md) 1절(임베딩 품질)에서 짧게 언급한 멀티모달 처리를 설계 수준으로 확장한다.

<br>

## 1. 세 가지 접근 방식

| 접근 | 색인 대상 | 질의 시 | 장점 | 단점 |
| --- | --- | --- | --- | --- |
| **A. 텍스트화(캡셔닝)** | 이미지·표·차트를 VLM으로 텍스트 설명·마크다운으로 변환해 텍스트 임베딩 | 기존 텍스트 RAG와 동일 | 기존 파이프라인 재사용, 검색·생성 모두 텍스트 모델로 가능, 비용 예측 쉬움 | 변환 단계에서 정보 손실, VLM 캡션의 오류가 색인에 고정됨 |
| **B. 멀티모달 임베딩** | 이미지와 텍스트를 같은 벡터 공간에 임베딩(CLIP 계열, 멀티모달 임베딩 API) | 텍스트 질의로 이미지 직접 검색, 이미지 질의도 가능 | 변환 손실 없음, 이미지 검색 자연스러움 | 세밀한 텍스트 내용(표의 숫자)은 약함, 생성 단계에 VLM 필요 |
| **C. 페이지 이미지 검색(ColPali 계열)** | 문서 페이지를 이미지 그대로 VLM 기반 다중 벡터로 임베딩 | 텍스트 질의로 페이지 이미지 검색, 검색된 페이지 이미지를 VLM에 입력 | 파싱·OCR 단계 제거, 레이아웃·표·차트를 통째로 보존, 파싱 오류 없음 | 다중 벡터로 저장 비용 큼, 생성 단계 VLM 토큰 비용 큼, 도구 생태계가 상대적으로 신생 |

실무에서는 **A를 기본으로 두고 C를 보완**하는 조합이 많다. 텍스트 위주 문서는 A로 처리해 비용을 낮추고, 표·차트·도해가 핵심인 문서(재무 보고서, 기술 도면, 슬라이드)는 C로 페이지 단위 검색을 붙인다. B는 상품 이미지 검색처럼 이미지 자체가 검색 대상인 경우에 쓴다.

<br>

## 2. 문서 파싱: 텍스트화 접근의 핵심

접근 A의 품질은 파싱 단계에서 결정된다. PDF에서 텍스트를 뽑는 것과 문서의 구조를 복원하는 것은 다른 일이다.

**파싱 파이프라인**

```
원본 문서 (PDF, PPTX, DOCX, 이미지)
   │
   ▼
[레이아웃 분석] ─ 페이지를 블록(본문, 제목, 표, 그림, 캡션, 머리말·꼬리말)으로 분할, 읽기 순서 복원
   │
   ├─ 본문·제목 → 텍스트 추출 (디지털 PDF) 또는 OCR (스캔)
   ├─ 표 → 구조 인식 → 마크다운/HTML 표로 변환 (병합 셀, 다단 헤더 보존)
   ├─ 그림·차트 → VLM 캡셔닝 ("2023~2025년 분기별 매출 추이 막대 차트. 2024 Q3 최고치 …")
   │              + 차트는 데이터 추출 시도 (축·수치)
   └─ 수식 → LaTeX
   │
   ▼
[구조화 문서] ─ 계층(장·절), 블록 유형, 페이지 번호, 원본 좌표를 메타데이터로 보존
   │
   ▼
[청킹] ─ 구조 경계 기준 분할, 표·그림은 캡션·주변 문단과 함께 하나의 청크
```

**도구**

| 구분 | 예 | 특징 |
| --- | --- | --- |
| 오픈소스 파서 | Docling(IBM), Marker, MinerU, Unstructured, PyMuPDF(텍스트·좌표) | 레이아웃 모델 + 표 인식 내장. 자체 호스팅 가능, 품질은 문서 유형별 편차 |
| VLM 직접 파싱 | 페이지 이미지를 VLM에 넣고 마크다운 출력 요청 | 복잡한 레이아웃·손글씨·비정형 문서에 강함. 페이지당 비용, 환각(없는 숫자 생성) 위험 |
| 클라우드 문서 AI | Azure Document Intelligence, Google Document AI, AWS Textract | 표·양식 인식 성숙, 관리형. 문서가 외부로 나감 |
| OCR 엔진 | PaddleOCR, Tesseract, 상용 OCR | 스캔 문서 텍스트 추출. 한국어는 엔진별 차이가 크므로 반드시 비교 |

**설계 포인트**

- **표는 표로 남긴다**: 표를 평문으로 펼치면 "행 3, 열 2가 얼마인가" 류의 질문에 답하지 못한다. 마크다운·HTML 표로 보존하고, 큰 표는 헤더를 각 분할 청크에 반복해 넣는다. 표 요약("이 표는 지역별 분기 매출을 담는다")을 함께 생성해 검색용으로 쓰고, 생성 단계에는 원본 표를 넘긴다.
- **그림 캡션은 질문을 예상해 쓴다**: "막대 차트"보다 "X축 분기, Y축 매출(억 원), 2024 Q3 142억으로 최고, 이후 하락"처럼 질의될 만한 정보를 담게 VLM 프롬프트를 설계한다. 캡션에 원본 이미지 참조를 남겨 생성 단계에서 이미지를 다시 볼 수 있게 한다.
- **한국어 문서**: 한국어 OCR·레이아웃 분석은 영어 대비 품질 편차가 크다. 파서 후보를 자사 문서 샘플 50~100페이지로 비교 평가한 뒤 고른다. 세로쓰기·한자 혼용·양식 문서는 별도 확인이 필요하다.
- **파싱 결과를 검증한다**: 문서 유형별 샘플에서 표 셀 정확도, 읽기 순서 정확도, 누락 블록 비율을 측정한다. 파싱 오류는 색인에 고정되어 검색·생성 모두를 망치므로, 파싱 품질 평가는 RAG 평가의 첫 단계다.

<br>

## 3. 페이지 이미지 검색(ColPali 계열)

접근 C는 파싱을 건너뛴다. 문서 페이지를 이미지로 렌더링하고, VLM 기반 인코더가 페이지를 수백 개의 패치 벡터(다중 벡터)로 표현한다. 질의는 텍스트를 토큰 벡터로 만들고, 질의 토큰과 페이지 패치 간 최대 유사도의 합(late interaction, ColBERT 방식)으로 점수를 매긴다.

**장점이 두드러지는 경우**

- 표·차트·도해·레이아웃이 의미를 담는 문서(재무제표, 기술 도면, 인포그래픽, 슬라이드)
- 파싱이 어려운 문서(복잡한 다단 레이아웃, 스캔 품질 불량, 손글씨 주석)
- 파싱 파이프라인 구축·유지 비용을 피하고 싶은 초기 단계

**비용과 대응**

- **저장**: 페이지당 벡터가 수백 개라 단일 벡터 대비 저장·검색 비용이 크다. 벡터 양자화(이진화·INT8), 패치 풀링으로 벡터 수 축소, 2단계 검색(단일 벡터 근사 검색으로 후보 → 다중 벡터로 재정렬)이 표준 대응이다.
- **생성**: 검색된 페이지 이미지를 VLM에 넣으면 페이지당 수백~수천 토큰이 든다. 상위 3~5페이지로 제한하고, 텍스트 질문이면 접근 A의 텍스트 청크와 하이브리드로 결합한다.
- **벡터 DB 지원**: 다중 벡터·late interaction을 네이티브로 지원하는 벡터 DB(Vespa, Qdrant 등)를 확인한다. 미지원이면 후보 검색과 재정렬을 애플리케이션에서 나눠 구현한다.

**대표 모델**: ColPali, ColQwen 계열(오픈소스), 그리고 주요 임베딩 API 제공사의 멀티모달·문서 이미지 임베딩. 벤치마크는 ViDoRe를 참고한다.

<br>

## 4. 검색과 생성 단계의 조정

멀티모달 문서가 색인되면 검색·생성 단계도 달라진다.

**검색**

- **하이브리드**: 텍스트 청크(BM25 + 텍스트 임베딩)와 페이지 이미지(다중 벡터)를 별도 인덱스로 두고 RRF로 융합한다. 표의 숫자 질의는 텍스트 인덱스가, 차트 추세 질의는 이미지 인덱스가 잡는 식으로 상호 보완한다.
- **모달리티 라우팅**: 질의를 분류해("이 차트에서", "표의 합계", "사진 속 제품") 어느 인덱스에 가중치를 둘지 정한다. 단순 분류기나 SLM으로 충분하다([소형 언어 모델과 온디바이스·엣지 추론](./small-language-models-edge.md)).
- **부모 확장**: 표·그림 청크가 검색되면 같은 페이지의 본문이나 캡션·주변 문단을 함께 가져온다. 그림만 있고 설명이 없으면 생성 단계가 맥락을 놓친다.
- **리랭킹**: 멀티모달 리랭커(질의 + 이미지·텍스트 쌍을 함께 보고 점수)가 있으면 사용하고, 없으면 VLM에 "이 페이지가 질문에 관련 있는가"를 이진 판정시켜 상위 후보를 걸러낸다.

**생성**

- **VLM에 원본을 준다**: 검색된 것이 표·차트·이미지라면 캡션이 아닌 **원본 이미지(또는 원본 표)**를 VLM 입력에 넣는다. 캡션은 검색용이고, 답변은 원본을 보고 해야 정확하다.
- **인용을 시각적으로**: 응답에 "출처: 2024 연차보고서 p.37, 표 12"처럼 페이지·블록을 명시하고, UI에서 해당 페이지 이미지의 영역을 하이라이트한다. 파싱 단계에서 보존한 원본 좌표가 여기에 쓰인다. 멀티모달 RAG에서 신뢰를 주는 가장 효과적인 장치다.
- **숫자는 검증한다**: VLM은 차트에서 숫자를 읽을 때 오차를 낸다. 표에서 추출된 구조화 데이터가 있으면 그것을 우선하고, 차트 판독값은 "차트 판독 기준 약 142억"처럼 불확실성을 표기한다.
- **응답에 이미지 포함**: 질문에 따라 답변에 관련 그림·표 자체를 포함하는 것이 텍스트 설명보다 낫다. 응답 형식에 이미지 참조를 허용한다.

## 5. 평가

텍스트 RAG 평가([RAG·LLM 평가 데이터세트 구축과 오프라인 평가 하네스](./llm-evaluation-harness.md))에 다음을 추가한다.

| 층 | 추가 지표 | 방법 |
| --- | --- | --- |
| **파싱** | 표 셀 정확도, 읽기 순서 정확도, 블록 누락률, OCR 문자 오류율 | 문서 유형별 골든 샘플 50~100페이지에 사람 라벨 |
| **검색** | 모달리티별 Recall@k(정답이 표·그림·본문인 질의를 구분), 페이지 단위 Recall | 평가 세트에 정답 페이지·블록 ID 기록 |
| **생성** | 시각 근거 일치(답의 숫자가 원본 표·차트와 일치하는가), 인용 위치 정확도 | 표 질의는 정답 값 비교로 자동화, 차트 질의는 허용 오차 설정 |
| **비용** | 문서당 색인 비용(파싱·캡셔닝·임베딩), 질의당 생성 토큰(이미지 입력 포함) | 접근 A/C 간 비교의 핵심 |

평가 세트에는 **정답이 표에만 있는 질의, 차트에만 있는 질의, 본문과 그림을 함께 봐야 하는 질의**를 의도적으로 배치한다. 텍스트 위주 세트로 평가하면 멀티모달 처리의 효과가 보이지 않는다.

## 6. 아키텍처 선택 가이드

| 문서 특성 | 권장 접근 | 비고 |
| --- | --- | --- |
| 텍스트 위주, 표 일부(사내 위키, 정책 문서) | A | 표 구조 보존만 신경 쓰면 충분 |
| 표·차트 중심(재무·실적 보고서, 데이터 시트) | A + C 하이브리드 | 표는 파싱해 정확한 숫자 확보, 차트·레이아웃은 페이지 이미지로 |
| 도해·도면 중심(기술 매뉴얼, 설계도) | C 우선 | 파싱이 의미를 잃음. 생성은 VLM 필수 |
| 스캔·양식 문서(계약서, 신청서) | 클라우드 문서 AI 또는 VLM 파싱 → A | 양식 필드 추출은 전용 도구가 성숙 |
| 상품 이미지·사진 아카이브 | B | 이미지 검색 자체가 목적. 텍스트 메타데이터와 하이브리드 |
| 슬라이드·프레젠테이션 | C | 페이지 단위 의미가 강하고 레이아웃이 정보 |

어느 경우든 **원본 파일과 페이지 이미지를 보관**한다. 파서·임베딩 모델·VLM은 빠르게 개선되므로 재색인이 반복되며, 원본이 있어야 재처리가 가능하다. 색인 결과에는 파서 버전·모델 버전을 메타데이터로 남겨 어떤 문서가 어떤 파이프라인으로 처리되었는지 추적한다.

<br>
<br>

멀티모달 RAG의 본질은 "이미지를 다룬다"가 아니라 **문서가 원래 가진 구조와 시각 정보를 잃지 않고 검색·생성에 전달하는 것**이다. 텍스트 RAG에서 청킹이 품질을 좌우했듯, 멀티모달 RAG에서는 파싱(또는 파싱을 건너뛰는 선택)이 품질을 좌우한다. 그리고 답변이 표와 차트의 숫자를 인용하는 순간, 근거를 원본 위치로 보여주는 인터페이스가 신뢰의 전부가 된다.
