# 컨텍스트 엔지니어링

프롬프트 엔지니어링이 "모델에게 무엇을 어떻게 말할 것인가"를 다듬는 일이었다면, 컨텍스트 엔지니어링(context engineering)은 **모델이 한 번의 호출에서 보는 모든 것**, 즉 시스템 프롬프트·대화 이력·검색 문서·도구 정의·도구 결과·메모리를 한정된 컨텍스트 창 예산 안에 무엇을 어떤 순서와 형태로 넣을지 설계하는 일이다. 책 12.3.1(프롬프트ㆍ컨텍스트ㆍ미세 조정 비교)이 세 수단을 비교했다면, 이 문서는 그중 컨텍스트라는 수단이 에이전트·RAG 시대에 어떻게 독립된 설계 영역으로 커졌는지를 다룬다.

[시스템 프롬프트 템플릿](./system-prompt-template.md), [RAG 품질 저하 요인과 대응 전략](./rag-quality-risks.md), [LLM 에이전트와 도구 호출 아키텍처](./llm-agent-architecture.md)는 각각 컨텍스트의 한 구성 요소를 다룬다. 이 문서는 그 위에서 구성 요소 전체를 하나의 예산으로 관리하는 관점을 제공한다.

<br>

## 1. 왜 "프롬프트"에서 "컨텍스트"로 옮겨갔는가

단일 호출 시대의 입력은 시스템 프롬프트와 사용자 질문 두 조각이었다. 에이전트와 RAG가 보편화되면서 한 호출의 입력은 다음처럼 커졌다.

| 구성 요소 | 출처 | 특성 |
| --- | --- | --- |
| 시스템 프롬프트 | 개발자 | 고정, 매 호출 반복 |
| 도구 정의(스키마) | 개발자 | 고정, 도구 수에 비례해 커짐 |
| few-shot 예시 | 개발자 | 고정 또는 질의별 선택 |
| 검색된 문서 | RAG 파이프라인 | 질의별 가변, 크기가 큼 |
| 대화 이력 | 사용자·모델 | 턴이 지날수록 누적 |
| 도구 결과 | 외부 시스템 | 크기 예측 불가, 종종 매우 큼 |
| 메모리(사용자 정보, 과거 결정) | 저장소 | 질의별 검색 |

이 구성 요소들은 서로 자리를 다툰다. 도구 결과가 커지면 대화 이력이 밀리고, 검색 문서를 많이 넣으면 예시를 줄여야 한다. 컨텍스트 창이 수십만 토큰으로 커졌어도 문제는 사라지지 않았다. 컨텍스트가 길어질수록 **비용과 지연이 선형으로 늘고**, 모델이 중간에 놓인 정보를 놓치는 현상(lost in the middle)과 무관한 정보에 끌려가는 현상(context distraction)이 커지며, 프리픽스 캐시 적중률이 떨어진다. 결국 "얼마나 많이 넣을 수 있는가"가 아니라 "무엇을 넣지 않을 것인가"가 설계의 중심이 되었다.

<br>

## 2. 컨텍스트 예산 설계

컨텍스트를 하나의 예산으로 보고 구성 요소별 상한을 정한다. 다음은 128K 컨텍스트 모델을 쓰는 사내 문서 Q&A 에이전트의 예산 배분 예시다.

| 구성 요소 | 예산(토큰) | 비고 |
| --- | --- | --- |
| 시스템 프롬프트 + 도구 정의 | 4K | 고정. 프리픽스 캐시 대상 |
| 메모리(사용자 프로필·최근 결정) | 1K | 검색 후 요약 형태로 주입 |
| 검색 문서 | 12K | 상위 6~8개 청크, 리랭킹 후 |
| 대화 이력 | 8K | 초과 시 오래된 턴을 요약으로 대체 |
| 도구 결과(현재 스텝) | 6K | 초과 시 잘라내고 "전체 N건 중 상위 k건" 표기 |
| 응답 여유 | 4K | 출력 토큰 상한 |
| **합계** | **35K** | 창 한도 대비 27%. 나머지는 예외 상황 여유 |

창 한도의 30~40% 이내로 운영하는 편이 비용·지연·품질 모두에 유리하다는 것이 실무의 경험적 기준이다. 예산은 요청 유형별로 달라질 수 있으므로(단순 조회 vs. 복합 분석), 라우팅 단계에서 유형을 판별해 예산 프로필을 고르는 구조도 흔하다.

**예산 초과 시 우선 삭감 순서**

1. 오래된 도구 결과 → 참조 ID만 남기고 본문 제거
2. 오래된 대화 턴 → 구조화 요약으로 대체
3. 검색 문서 → 리랭킹 점수 하위부터 제거
4. few-shot 예시 → 질의와 가장 유사한 1~2개만 유지
5. 시스템 프롬프트·도구 정의는 마지막까지 유지

## 3. 핵심 기법

### 3.1 배치와 순서

- **고정 부분을 앞에, 가변 부분을 뒤에**: 시스템 프롬프트·도구 정의·예시처럼 매 호출 동일한 내용은 앞쪽에 고정 배치해 프리픽스 캐싱의 혜택을 받는다. 타임스탬프나 사용자 ID처럼 매번 바뀌는 값을 시스템 프롬프트 첫 줄에 넣는 실수가 캐시 적중률을 0으로 만든다. [LLM 추론 서빙 최적화](./llm-inference-serving.md) 2절을 참고한다.
- **중요한 정보는 양 끝에**: 모델은 컨텍스트의 시작과 끝을 잘 기억하고 중간을 놓치는 경향이 있다. 가장 관련성 높은 검색 문서를 첫 번째와 마지막에 배치하고, 핵심 지시는 시스템 프롬프트(앞)와 사용자 메시지 끝(뒤)에 반복한다.
- **구조 태그**: 구성 요소마다 `<documents>`, `<tool_result>`, `<memory>` 같은 태그로 경계를 명시한다. 모델이 출처를 구분해 인용할 수 있고, 지시와 데이터를 분리하는 보안 효과도 있다.

### 3.2 압축

- **도구 결과 가공**: 원시 JSON·HTML을 그대로 넣지 않는다. 도구 계층에서 필요한 필드만 추출하고 표 형태로 정리해 반환한다. 웹 페이지는 본문 텍스트만, DB 결과는 상위 N행과 집계값만 넘긴다. 이 한 가지가 토큰 사용량을 절반 이하로 줄이는 경우가 많다.
- **대화 이력 요약**: 일정 턴 수나 토큰 수를 넘으면 오래된 부분을 "지금까지의 목표, 확인된 사실, 내린 결정, 남은 작업" 형식의 구조화 요약으로 대체한다. 자유 서술 요약보다 정보 손실이 적고, 이후 턴에서 참조하기 쉽다.
- **검색 문서 압축**: 청크 전체 대신 질의와 관련된 문장만 추출(extractive compression)하거나, 여러 청크를 하나의 요약으로 합친다. 정보 손실 위험이 있으므로 원문 참조 ID를 남기고, 필요하면 모델이 도구로 원문을 다시 조회할 수 있게 한다.
- **프롬프트 자체의 압축**: 시스템 프롬프트가 길어지면 규칙을 우선순위별로 정리하고 중복을 제거한다. 지침 5~7개가 50개보다 잘 지켜진다는 것은 여전히 유효하다.

### 3.3 격리

- **서브 에이전트로 컨텍스트 분리**: 큰 문서 분석, 대량 검색 결과 검토처럼 컨텍스트를 많이 소비하는 작업은 별도 에이전트에게 넘기고 **결론만** 받아온다. 주 에이전트의 컨텍스트는 깨끗하게 유지되고, 서브 에이전트는 자기 작업에만 집중한다. 다중 에이전트 구조가 정당화되는 가장 큰 이유가 이 컨텍스트 격리다.
- **외부 저장소 활용**: 중간 결과·계획·긴 참조 자료는 파일이나 키-값 저장소에 두고, 컨텍스트에는 "어디에 무엇이 있는지"만 남긴다. 모델이 필요할 때 도구로 읽어온다. 컨텍스트 창을 작업 메모리(RAM)로, 외부 저장소를 디스크로 보는 관점이다.
- **도구 정의의 동적 노출**: 도구가 수십 개를 넘으면 전체 스키마를 매번 넣지 않고, 현재 작업과 관련된 도구만 검색해 노출한다. 도구 정의도 컨텍스트 소비자라는 점을 잊기 쉽다.

### 3.4 선택: 긴 컨텍스트인가, 검색인가

컨텍스트 창이 커지면서 "문서를 통째로 넣으면 RAG가 필요 없지 않은가"라는 질문이 반복된다. 판단 기준은 다음과 같다.

| 기준 | 통째로 넣기(long context) | 검색(RAG) |
| --- | --- | --- |
| 자료 크기 | 수십 페이지 이내, 창의 30% 이하 | 그 이상 |
| 질의 빈도 | 같은 자료에 소수 질의 | 같은 자료에 다수 질의(캐시로 상쇄 가능) |
| 갱신 빈도 | 낮음 | 높음(색인 갱신이 프롬프트 갱신보다 쉬움) |
| 근거 추적 | 어려움(전체가 근거) | 쉬움(검색 청크가 근거) |
| 비용 | 질의당 고비용 | 색인 고정비 + 질의당 저비용 |
| 접근 제어 | 어려움 | 문서 단위 권한 필터 가능 |

실무에서는 둘을 조합한다. 검색으로 후보를 좁힌 뒤, 선택된 문서는 청크가 아닌 **전체**를 넣어 문맥 단절을 피하는 방식(문서 단위 검색, 청크 단위 검색 후 부모 문서 확장)이 흔하다.

## 4. 메모리 설계

여러 세션에 걸쳐 유지되는 정보를 컨텍스트에 어떻게 넣을지도 컨텍스트 엔지니어링의 일부다.

- **무엇을 기억하는가**: 사용자 선호·제약(언어, 형식, 금지 사항), 과거 결정과 이유, 진행 중인 작업 상태. 대화 원문을 통째로 저장하는 것은 검색 노이즈만 늘린다.
- **어떻게 저장하는가**: 구조화된 사실 목록(키-값 또는 짧은 문장)이 자유 서술보다 검색·갱신·삭제가 쉽다. 사실마다 출처(사용자가 직접 말했는가, 모델이 추론했는가)와 시점을 붙인다.
- **어떻게 주입하는가**: 매 호출에 전부 넣지 않고, 현재 질의와 관련된 항목만 검색해 요약 형태로 넣는다. 시스템 프롬프트 뒤, 검색 문서 앞이 일반적인 위치다.
- **무엇을 기억하지 않는가**: 개인정보·민감 정보는 저장 단계에서 걸러야 한다. 책 13.4의 개인정보 보호 원칙이 메모리 설계에 그대로 적용된다. 사용자가 삭제를 요청하면 파생 정보까지 지울 수 있는 구조여야 한다.

<br>

## 5. 측정

컨텍스트 설계는 감으로 하면 안 된다. 다음 지표를 트레이스에 기록한다.

| 지표 | 의미 | 개선 신호 |
| --- | --- | --- |
| 호출당 입력 토큰 분포(p50/p95) | 예산 준수 여부 | p95가 예산을 넘으면 삭감 규칙 점검 |
| 구성 요소별 토큰 비율 | 어디에 예산이 쓰이는가 | 도구 결과가 50%를 넘으면 도구 계층 가공 부족 |
| 프리픽스 캐시 적중률 | 고정 부분 배치의 적절성 | 낮으면 가변 값이 앞에 섞여 있음 |
| 컨텍스트 활용률 | 넣은 문서 중 응답에 실제 인용된 비율 | 낮으면 검색 후보 수 과다 |
| 요약 후 정보 손실 | 요약 전후 평가 점수 차이 | 손실 크면 요약 형식 재설계 |

평가 방법은 [RAG·LLM 평가 데이터세트 구축과 오프라인 평가 하네스](./llm-evaluation-harness.md)를 따르되, "같은 질의에 컨텍스트 구성만 바꾼" 변형을 비교하는 실험을 추가한다. 문서 수를 8개에서 4개로 줄였을 때, 이력을 요약으로 바꿨을 때 점수가 유지되는지를 확인하는 것이 비용 최적화의 근거가 된다.

<br>
<br>

컨텍스트 엔지니어링의 원칙은 결국 **모델에게 필요한 것만, 필요한 시점에, 찾기 쉬운 형태로** 보여주는 것이다. 이는 사람에게 일을 맡길 때 관련 자료를 정리해 건네는 것과 같다. 서류함을 통째로 넘기면 유능한 사람도 일을 못 한다. 컨텍스트 창이 아무리 커져도 이 원칙은 바뀌지 않으며, 오히려 창이 커질수록 무엇을 넣지 않을지 결정하는 규율이 더 중요해진다.
