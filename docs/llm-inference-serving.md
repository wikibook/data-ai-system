# LLM 추론 서빙 최적화

대규모 언어 모델(LLM)의 서빙은 일반적인 딥러닝 모델 서빙과 같은 원칙을 따르지만, 토큰을 한 개씩 순차적으로 생성하는 자기회귀(autoregressive) 구조 때문에 병목의 위치와 최적화 수단이 크게 다르다. 책 12.2.4(LLM 최적화 전략)에서 개념적으로 소개한 내용을, 실제 서빙 엔진을 선택하고 운영할 때 필요한 수준으로 구체화한다.

이 문서는 [모델 서빙 시 트레이드오프 고려사항](./model-serving-tradeoffs.md)의 6절에서 요약한 LLM 서빙의 특성을 전제로 한다.

<br>

## 1. 추론의 두 단계: Prefill과 Decode

LLM 추론은 성격이 전혀 다른 두 단계로 나뉜다.

- **Prefill(프리필)**: 입력 프롬프트 전체를 한 번에 처리해 각 토큰의 Key/Value를 계산하고 첫 토큰을 생성한다. 입력 길이에 비례하는 대규모 행렬 연산이므로 **연산(compute) 바운드**이며, GPU 활용률이 높다.
- **Decode(디코드)**: 이후 토큰을 한 개씩 생성한다. 매 스텝마다 모델 가중치 전체와 누적된 KV 캐시를 메모리에서 읽어야 하지만 연산량은 토큰 하나 분량에 그친다. 따라서 **메모리 대역폭 바운드**이며, 단일 요청만 처리하면 GPU 연산 유닛의 대부분이 놀게 된다.

이 구조 때문에 LLM 서빙의 지연 시간 지표는 둘로 나뉜다.

| 지표 | 정의 | 지배 요인 | 사용자 체감 |
| --- | --- | --- | --- |
| **TTFT**(Time To First Token) | 요청 수신부터 첫 토큰 출력까지 | Prefill 시간 + 큐 대기 | "응답이 시작되는가" |
| **TPOT**(Time Per Output Token) | 이후 토큰 하나를 생성하는 평균 시간 | Decode 스텝 시간, 동시 배치 크기 | "읽는 속도보다 빠른가" |
| **E2E 지연** | TTFT + TPOT × 출력 토큰 수 | 출력 길이 | 전체 대기 시간 |

스트리밍 응답을 사용하면 사용자는 TTFT 이후부터 내용을 읽기 시작하므로, TPOT가 사람의 읽기 속도(대략 초당 10~20 토큰)보다 빠르기만 하면 E2E 지연이 길어도 체감 품질이 크게 떨어지지 않는다. 즉, 대화형 서비스에서는 TTFT를 최우선으로, 배치성 생성(요약, 문서 변환)에서는 처리량을 최우선으로 최적화하는 것이 일반적이다.

<br>

## 2. 메모리 병목: KV 캐시

Decode 단계에서 이전 토큰의 Key/Value를 다시 계산하지 않도록 저장해 두는 것이 KV 캐시다. 계산은 줄지만 GPU 메모리를 요청마다, 토큰마다 소비한다.

**KV 캐시 크기 계산**

```
KV 캐시(바이트) = 2 × 레이어 수 × KV 헤드 수 × 헤드 차원 × 시퀀스 길이 × 배치 크기 × 정밀도(바이트)
```

예를 들어 Llama 2 7B(32 레이어, 32 헤드, 헤드 차원 128, FP16)는 토큰 하나당 약 0.5MB를 소비한다. 4,096 토큰 요청 하나가 약 2GB, 80GB GPU에서 가중치 14GB를 제외하면 동시 처리 가능한 4K 요청은 30개 안팎에 그친다. 이 계산이 곧 "동시 접속 수 상한"을 결정하므로, LLM 서빙 용량 계획은 연산량이 아닌 KV 캐시 메모리 예산에서 시작해야 한다.

**메모리 효율화 기법**

- **PagedAttention**: 운영체제의 페이징처럼 KV 캐시를 고정 크기 블록으로 나눠 비연속적으로 할당한다. 요청별로 최대 길이만큼 미리 예약할 때 발생하던 내부 단편화(전체 메모리의 60~80%가 낭비되는 경우도 있었다)를 제거해 동시 배치 크기를 수 배 늘린다. vLLM이 이 기법으로 널리 알려졌다.
- **프리픽스 캐싱(prefix caching)**: 여러 요청이 공유하는 앞부분(시스템 프롬프트, few-shot 예시, RAG의 공통 문서)의 KV 캐시를 재사용한다. 시스템 프롬프트가 수천 토큰인 서비스에서는 Prefill 비용과 TTFT를 크게 줄인다. API 제공사들의 "prompt caching" 기능도 같은 원리다.
- **KV 캐시 양자화**: KV 캐시를 FP8 또는 INT8로 저장해 메모리를 절반으로 줄인다. 가중치 양자화보다 정확도 영향이 작은 편이지만, 긴 문맥에서의 품질 저하를 벤치마크로 확인해야 한다.
- **아키텍처 수준의 절감**: GQA(Grouped-Query Attention)·MQA(Multi-Query Attention)는 KV 헤드 수를 줄여 캐시를 4~8배 절감하며, MLA(Multi-head Latent Attention)는 KV를 저차원으로 압축한다. 모델 선택 단계에서 이 구조를 채택한 모델을 고르는 것 자체가 서빙 비용 결정이다.

<br>

## 3. 스케줄링: Continuous Batching

일반 모델 서빙의 동적 배치는 요청 여러 개를 모아 한 번에 처리하고 함께 반환한다. LLM에 이를 그대로 적용하면 배치 안에서 가장 긴 응답이 끝날 때까지 짧은 요청도 기다려야 하고, 끝난 요청의 슬롯은 비어 있는 채로 남는다.

**Continuous batching(iteration-level scheduling)** 은 Decode 스텝 단위로 배치를 재구성한다. 어떤 요청이 종료 토큰을 생성하면 그 즉시 슬롯을 대기 중인 새 요청에 넘기고, 새 요청의 Prefill을 진행 중인 다른 요청의 Decode와 같은 스텝에 섞어 처리한다. 이로써 GPU 유휴가 거의 사라지고, 정적 배치 대비 처리량이 수 배에서 수십 배까지 개선된다.

운영 시 조정하는 주요 파라미터는 다음과 같다.

| 파라미터(vLLM 기준 명칭) | 역할 | 트레이드오프 |
| --- | --- | --- |
| `max_num_seqs` | 동시 처리 요청 수 상한 | 높이면 처리량↑, TPOT↑ |
| `max_num_batched_tokens` | 한 스텝에 처리할 토큰 수 상한 | Prefill 요청이 Decode 요청을 지연시키는 정도를 제어 |
| `gpu_memory_utilization` | KV 캐시에 할당할 GPU 메모리 비율 | 높이면 동시 처리↑, OOM 위험↑ |
| `enable_chunked_prefill` | 긴 프롬프트의 Prefill을 여러 스텝으로 분할 | 긴 입력이 다른 요청의 TPOT를 튀게 하는 현상 완화 |
| `enable_prefix_caching` | 공통 프리픽스 KV 재사용 | 메모리 관리 오버헤드 소폭 증가 |

## 4. 경량화: 양자화와 추측 디코딩

**가중치 양자화**

| 방식 | 정밀도 | 특징 | 적합한 상황 |
| --- | --- | --- | --- |
| FP8 | 8비트 부동소수 | H100 등 최신 GPU에서 하드웨어 가속, 정확도 손실 거의 없음 | 최신 GPU에서 처리량 확보 |
| INT8 (LLM.int8, SmoothQuant) | 8비트 정수 | 가중치·활성화 모두 양자화, 이상치(outlier) 처리가 관건 | 범용 GPU에서 메모리 절반 |
| GPTQ | 4비트 (가중치만) | 보정 데이터로 레이어별 오차 최소화, 사후 양자화(PTQ) | 메모리 제약이 크고 지연보다 비용이 중요할 때 |
| AWQ | 4비트 (가중치만) | 활성화 크기 기준으로 중요한 가중치 채널을 보호, GPTQ보다 일반화가 좋은 편 | 4비트 배포의 사실상 기본 선택 |
| GGUF (llama.cpp) | 2~8비트 다양 | CPU·Apple Silicon 등 비GPU 환경 | 온디바이스·엣지 |

4비트 양자화는 메모리를 1/4로 줄이고 메모리 대역폭 바운드인 Decode 단계를 가속하지만, 배치 크기가 커지면 역양자화(dequantize) 오버헤드 때문에 처리량 이득이 줄어든다. 즉 **저동시성·저지연 환경에서는 4비트가, 고동시성·고처리량 환경에서는 FP8/INT8이 유리**한 경우가 많다. 양자화 후에는 perplexity뿐 아니라 실제 다운스트림 과제(자사 평가 데이터세트)로 품질 저하를 확인해야 한다.

**추측 디코딩(speculative decoding)**

작은 초안(draft) 모델이 토큰 여러 개를 빠르게 제안하고, 대형 모델이 한 번의 forward로 이를 병렬 검증해 맞은 만큼 수용한다. 출력 분포는 대형 모델 단독과 동일하게 유지되면서 TPOT가 2~3배 개선될 수 있다. 초안 모델 없이 모델 자체의 중간 레이어나 n-gram 통계를 활용하는 변형(Medusa, EAGLE, prompt lookup)도 있다. 코드 생성이나 정형화된 문서처럼 예측 가능성이 높은 출력에서 효과가 크고, 창의적 생성에서는 수용률이 낮아 이득이 줄어든다.

## 5. 서빙 엔진 비교

| 엔진 | 강점 | 유의점 | 적합한 경우 |
| --- | --- | --- | --- |
| **vLLM** | PagedAttention·continuous batching의 표준 구현, 폭넓은 모델·양자화 지원, OpenAI 호환 API, 활발한 커뮤니티 | 릴리스 주기가 빠라 버전 고정 필요 | 대부분의 자체 호스팅 시작점 |
| **TGI**(Text Generation Inference) | Hugging Face 생태계 통합, 안정적인 운영 도구 | 최신 최적화 반영이 vLLM보다 늦을 수 있음 | Hugging Face Hub 중심 워크플로 |
| **TensorRT-LLM** | NVIDIA GPU에서 최고 수준 처리량, FP8·인플라이트 배칭, Triton과 통합 | 모델별 엔진 빌드 필요, NVIDIA 전용, 빌드 시간·복잡도 | 대규모 트래픽에서 GPU 비용을 끝까지 줄여야 할 때 |
| **SGLang** | RadixAttention 기반 프리픽스 캐싱, 구조화 출력·다중 호출 프로그램에 강점 | 상대적으로 신생 | 에이전트·RAG처럼 프롬프트 공유가 많은 워크로드 |
| **llama.cpp / Ollama** | CPU·Apple Silicon·소형 GPU, 설치 간편 | 고동시성에는 부적합 | 개발용, 온디바이스, 소규모 내부 도구 |
| **Triton Inference Server** | 다중 프레임워크·다중 모델 통합 서빙, 앙상블 파이프라인 | LLM 전용 최적화는 TensorRT-LLM 백엔드에 의존 | LLM과 기존 ML 모델을 한 서빙 계층에서 운영 |

선택 순서는 대체로 다음과 같다. 먼저 vLLM으로 기준 성능을 확보하고, GPU 비용이 지배적이면 TensorRT-LLM으로 이전 비용 대비 이득을 측정하며, 워크로드가 에이전트·다중 호출 구조라면 SGLang을 비교한다. 소형 모델을 과제별로 계층화해 대형 모델 호출을 줄이는 전략은 [소형 언어 모델(SLM)과 온디바이스·엣지 추론](./small-language-models-edge.md)에서 다룬다. 자체 호스팅과 API 이용의 손익분기점은 GPU 활용률에 좌우되므로, 트래픽이 하루 중 일부 시간에 몰린다면 오토 스케일링을 포함한 총비용으로 비교해야 한다.

## 6. 병렬화와 배치 구성

단일 GPU에 모델이 실리지 않거나 처리량이 부족하면 병렬화가 필요하다.

- **텐서 병렬(TP)**: 각 레이어의 행렬을 여러 GPU에 분할한다. 노드 내 NVLink처럼 고대역폭 연결이 필수이며, 지연 시간을 줄이는 데 효과적이다. 일반적으로 노드 내 GPU 수(2, 4, 8)로 설정한다.
- **파이프라인 병렬(PP)**: 레이어를 GPU별로 나눠 순서대로 처리한다. 노드 간 통신에 비교적 관대하지만 파이프라인 버블로 지연이 늘어난다. 노드를 넘어야 할 때 TP와 조합한다.
- **데이터 병렬(복제)**: 모델 전체를 여러 인스턴스로 복제하고 로드 밸런서로 분배한다. 가장 단순하고 장애 격리에 유리하며, 모델이 GPU 하나에 들어가면 TP보다 처리량 대비 비용이 낫다.
- **Prefill/Decode 분리(disaggregated serving)**: 연산 바운드인 Prefill과 메모리 바운드인 Decode를 서로 다른 GPU 풀에서 처리하고 KV 캐시를 전송한다. 두 단계의 자원 요구가 달라 각각 독립적으로 스케일링할 수 있으며, 긴 프롬프트가 Decode 지연을 흔드는 현상을 근본적으로 막는다. 대규모 서비스에서 채택이 늘고 있다.

## 7. 운영 지표와 용량 계획

LLM 서빙 대시보드에는 최소한 다음 지표가 있어야 한다.

| 범주 | 지표 | 판단 기준 |
| --- | --- | --- |
| 지연 | TTFT p50/p95/p99, TPOT p50/p95 | TTFT p95가 SLO를 넘으면 큐 대기 또는 Prefill 병목 |
| 처리량 | 초당 생성 토큰 수, 초당 처리 요청 수 | GPU당 토큰/초가 벤치마크 대비 낮으면 배치 구성 점검 |
| 자원 | KV 캐시 사용률, 대기 큐 길이, 선점(preemption) 횟수 | KV 캐시 사용률 90% 이상·선점 발생은 용량 한계 신호 |
| 비용 | 1M 토큰당 비용(입력/출력 분리), GPU 시간당 처리 토큰 | API 단가와 직접 비교 |
| 품질 | 캐시 적중률, 추측 디코딩 수용률, 양자화 모델의 평가 점수 | 최적화가 품질을 깎고 있는지 감시 |

용량 계획은 "목표 동시 사용자 수 × 평균 컨텍스트 길이 → 필요한 KV 캐시 메모리 → GPU 수"의 순서로 계산한 뒤, 부하 테스트로 TTFT SLO를 만족하는 최대 동시 요청 수를 실측해 보정한다. 모델·양자화·엔진 조합이 바뀌면 이 실측을 반복해야 하므로, 부하 테스트를 배포 파이프라인의 일부로 자동화하는 것이 바람직하다.

LLM 서빙 최적화는 결국 **KV 캐시 메모리를 어떻게 아끼고, GPU를 어떻게 쉬지 않게 하며, 정밀도를 어디까지 낮출 수 있는가**의 세 질문으로 수렴한다. 엔진 선택보다 중요한 것은 자사 트래픽 패턴(동시성, 프롬프트 길이 분포, 출력 길이 분포)을 먼저 측정하는 일이다. 같은 모델이라도 짧은 프롬프트·짧은 응답의 챗봇과 긴 문서·짧은 응답의 RAG, 짧은 지시·긴 응답의 생성 도구는 최적의 설정이 전혀 다르기 때문이다.
