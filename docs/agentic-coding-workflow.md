# 에이전트 코딩 도구와 데이터·ML 개발 워크플로

Claude Code, Codex, Cursor, Gemini CLI 같은 에이전트 코딩 도구는 코드 자동 완성을 넘어, 저장소를 읽고 계획을 세워 파일을 수정하고 테스트를 실행한 뒤 결과를 보고 다시 고치는 **자율 실행 루프**를 갖는다. 데이터·ML 팀에서도 파이프라인 코드, 피처 로직, 학습 스크립트, SQL 변환, 인프라 정의(Terraform, Kubernetes 매니페스트)를 이 도구로 작성하는 것이 일상이 되었다. 책 7.4(CI/CD와 MLOps)가 다룬 개발 파이프라인은 이제 "사람이 코드를 쓰고 CI가 검증한다"에서 "에이전트가 코드를 쓰고, 사람과 CI가 검증한다"로 바뀌고 있다. 이 문서는 그 변화에 맞춰 데이터·ML 저장소와 팀 프로세스를 어떻게 정비해야 하는지를 정리한다.

이 문서는 에이전트 코딩 도구를 **쓰는 쪽**의 관점이다. 에이전트를 **만드는 쪽**의 설계는 [LLM 에이전트와 도구 호출 아키텍처](./llm-agent-architecture.md)에서 다룬다.

<br>

## 1. 무엇이 달라졌는가

| 관점 | 자동 완성 시대 | 에이전트 코딩 시대 |
| --- | --- | --- |
| 작업 단위 | 한 줄, 한 함수 | 이슈 하나("이 피처의 결측 처리를 바꾸고 테스트를 갱신해라") |
| 도구가 보는 범위 | 현재 파일 | 저장소 전체, 문서, 터미널 출력, 테스트 결과 |
| 도구가 하는 일 | 제안 | 파일 수정, 명령 실행, 커밋, PR 작성 |
| 사람의 역할 | 타이핑 | 과제 정의, 컨텍스트 제공, 결과 검토 |
| 병목 | 코드 작성 속도 | 검토 속도, 컨텍스트 품질, 검증 환경 |

핵심 전환은 **생산성의 병목이 작성에서 검증으로 옮겨간 것**이다. 에이전트가 하루에 PR을 10개 만들면, 팀은 그 10개를 검토할 수 있어야 한다. 검토 부담을 줄이는 유일한 방법은 에이전트가 스스로 검증할 수 있는 환경(테스트, 린트, 드라이런, 데이터 검증)을 갖추는 것이다. 이는 결국 소프트웨어 엔지니어링 기본기의 문제이며, 에이전트 도입은 그 기본기가 부족한 저장소를 가장 먼저 드러낸다.

<br>

## 2. 저장소를 에이전트가 읽을 수 있게 만들기

에이전트는 저장소에 있는 것만 안다. 팀원의 머릿속과 슬랙 스레드에만 있는 규칙은 에이전트에게 존재하지 않는다.

### 2.1 컨텍스트 파일

주요 도구는 저장소 루트의 컨텍스트 파일을 자동으로 읽는다. Claude Code는 `CLAUDE.md`, 여러 도구가 공통으로 `AGENTS.md`를 읽으며, Cursor는 `.cursor/rules/`를 쓴다. 한 파일을 정본으로 두고 나머지는 심볼릭 링크나 참조로 연결한다.

컨텍스트 파일에 담을 것은 다음과 같다. 길이는 A4 한두 장 이내로 유지하고, 상세 내용은 별도 문서로 링크한다. 컨텍스트 파일도 컨텍스트 예산을 소비한다([컨텍스트 엔지니어링](./context-engineering.md)).

```markdown
# 프로젝트 개요
- 목적: 상품 추천 피처 파이프라인. Databricks(Spark) → 피처 스토어(Valkey).
- 구조: `pipelines/`(배치 잡), `features/`(피처 정의), `serving/`(온라인 조회 API), `tests/`

# 명령
- 테스트: `make test` (단위) / `make test-integration` (로컬 Spark 필요)
- 린트·타입: `make lint`
- 파이프라인 드라이런: `make dry-run PIPELINE=<name> DATE=<yyyy-mm-dd>` — 실제 쓰기 없음
- 절대 실행 금지: `make deploy-*`, `dbt run --target prod`

# 규칙
- 피처 정의 변경 시 `features/CONTRACT.md`의 스키마도 함께 갱신하고 `make check-contract`를 통과시킨다.
- 새 피처는 반드시 `tests/features/`에 분포 테스트(null 비율, 범위)를 추가한다.
- SQL은 `sqlfluff` 규칙을 따른다. CTE 우선, 서브쿼리 중첩 금지.
- 시간은 UTC로 저장하고 표시 시에만 KST로 변환한다.
- 시크릿·연결 문자열은 코드에 넣지 않는다. `config/` 참조.

# 데이터 접근
- 개발 환경은 `dev` 카탈로그만 접근 가능하다. `prod` 데이터는 샘플 `data/samples/`를 사용한다.
- 실제 데이터 조회가 필요하면 사람에게 요청한다.

# 검토 기준
- PR 설명에 변경 이유, 영향 받는 피처, 실행한 검증 명령과 결과를 포함한다.
```

### 2.2 문서와 코드의 위치

- **결정의 이유를 남긴다**: "왜 이 피처는 7일 윈도우인가"가 코드 주석이나 ADR(Architecture Decision Record)에 있으면 에이전트가 함부로 바꾸지 않는다. 없으면 "더 좋아 보이는" 30일로 바꾼다.
- **데이터 계약을 저장소에 둔다**: 입력·출력 스키마, 품질 규칙이 파일로 있으면 에이전트가 변경의 영향을 판단하고 계약 검사를 실행할 수 있다. [데이터 계약과 스키마 진화](./data-contracts-schema-evolution.md)를 참고한다.
- **샘플 데이터를 둔다**: 실제 데이터에 접근하지 않고도 파이프라인을 끝까지 돌려볼 수 있는 소규모 샘플(수백~수천 행, 개인정보 제거)을 저장소나 접근 가능한 위치에 둔다. 에이전트가 자기 변경을 검증하는 데 필수다.
- **노트북은 스크립트로**: `.ipynb`는 에이전트가 읽고 수정하기 어렵고 diff도 보기 어렵다. 탐색은 노트북에서 하되, 파이프라인에 들어가는 로직은 `.py` 모듈로 옮기고 노트북은 그 모듈을 호출하게 한다. 이는 에이전트 이전부터 권장되던 관행이지만 이제 실질적 강제력이 생겼다.

## 3. 에이전트가 스스로 검증할 수 있는 환경

에이전트 루프의 품질은 "실행 → 결과 확인 → 수정"이 얼마나 빠르고 안전하게 돌아가는지에 달려 있다.

| 검증 수단 | 역할 | 데이터·ML 저장소에서의 구체화 |
| --- | --- | --- |
| **단위 테스트** | 로직 정확성 | 피처 계산 함수, 전처리, 후처리에 대해 작은 DataFrame 입력·출력 테스트. 로컬에서 수 초 내 완료 |
| **데이터 검증** | 출력 분포 | 샘플 데이터로 파이프라인 실행 후 스키마·null 비율·범위·행 수 검증(Great Expectations, pandera, dbt tests) |
| **드라이런** | 부작용 없는 실행 | 쓰기 대상을 임시 위치로 바꾸거나 실행 계획만 출력. Spark `explain`, dbt `--empty`, Airflow `dags test`, Terraform `plan` |
| **린트·타입·포맷** | 규약 준수 | ruff, mypy, sqlfluff. 에이전트는 린트 오류를 스스로 고칠 수 있으므로 규칙을 엄격하게 두어도 부담이 적다 |
| **계약 검사** | 스키마 호환성 | 피처·테이블 스키마 변경이 하위 호환인지 자동 판정 |
| **소규모 학습 실행** | 학습 코드 정상 동작 | 샘플 데이터·1 에폭·작은 모델로 학습 스크립트를 끝까지 실행. 지표 값이 아니라 "돌아가는지"를 확인 |
| **비용 추정** | 쿼리 비용 | 웨어하우스 쿼리의 스캔 바이트 추정(`EXPLAIN`, dry-run 모드)을 확인해 폭주 쿼리 방지 |

이 검증들이 **한 명령**(`make check`)으로 실행되고 결과가 명확한 성공/실패와 읽기 쉬운 오류 메시지로 나오면, 에이전트는 사람 개입 없이 여러 번 시도해 통과시킨다. 검증이 느리거나(30분 통합 테스트만 존재), 결과가 모호하거나(경고 200줄), 실행에 사람의 자격 증명이 필요하면 에이전트 루프는 끊어진다.

**격리된 실행 환경**

에이전트는 명령을 실행하므로 실수의 범위를 물리적으로 제한해야 한다.

- 개발 컨테이너(devcontainer)나 샌드박스에서 실행하고, 운영 자격 증명은 그 환경에 없게 한다.
- 개발용 카탈로그·버킷·네임스페이스를 분리하고, 에이전트 실행 환경의 권한을 거기로 한정한다. 책 13.2.2의 접근 제어 원칙이 개발 환경에도 적용되는 것이다.
- 도구의 권한 설정(허용 명령 목록, 파일 쓰기 범위, 네트워크)을 저장소 설정으로 관리한다. "모든 명령 자동 승인"은 격리된 환경에서만 쓴다.
- 브랜치나 git worktree를 작업마다 분리해 에이전트의 변경이 사람의 작업 중인 파일과 섞이지 않게 한다.

## 4. 과제 정의: 에이전트에게 무엇을 어떻게 맡기는가

### 4.1 잘 맞는 과제와 맞지 않는 과제

| 잘 맞는 과제 | 맞지 않는 과제 |
| --- | --- |
| 명세가 명확하고 검증 가능한 변경(스키마 추가, 테스트 작성, 리팩터링, 마이그레이션) | 요구사항 자체가 불명확한 탐색("이 지표가 왜 떨어졌는지 봐줘"에서 원인 가설 수립) |
| 반복적·기계적 작업(보일러플레이트, 여러 파일에 같은 패턴 적용, 문서 갱신) | 도메인 판단이 필요한 결정(피처 윈도우 길이, 라벨 정의, 지표 임곗값) |
| 기존 패턴을 따르는 신규 코드(새 파이프라인을 기존 파이프라인 구조로) | 실제 운영 데이터를 봐야 하는 디버깅(데이터 접근 권한 문제) |
| 오류 메시지가 명확한 버그 수정 | 실험 설계와 결과 해석 |

데이터·ML 작업에서 에이전트에게 맡길 부분과 사람이 할 부분을 나누는 기준은 **"검증 가능한가"** 다. 피처 계산 로직 구현은 테스트로 검증되므로 맡기고, 어떤 피처가 유효한지는 실험 결과를 사람이 해석해야 하므로 사람이 한다. 탐색적 분석에서는 에이전트에게 "가설 A를 확인하는 쿼리와 시각화를 만들어라"처럼 가설을 사람이 제시하고 확인 작업을 맡기는 분업이 효과적이다.

### 4.2 과제 작성법

- **완료 조건을 명시한다**: "테스트가 통과하고, `make check-contract`가 성공하고, PR 설명에 검증 결과가 포함되면 완료".
- **범위를 한정한다**: "`features/user_activity.py`만 수정하고 다른 피처는 건드리지 않는다". 범위가 없으면 에이전트는 "개선"을 계속한다.
- **하지 말 것을 적는다**: "운영 카탈로그 조회 금지", "의존성 추가 금지", "기존 테스트 삭제 금지".
- **큰 과제는 계획을 먼저 받는다**: 구현 전에 변경 파일 목록과 접근 방식을 제시하게 하고 사람이 승인한 뒤 진행한다. 방향이 틀린 대규모 변경을 검토하는 비용이 계획 검토 비용보다 훨씬 크다.
- **이슈 트래커와 연결한다**: 과제 정의를 이슈에 쓰고 에이전트가 이슈 번호로 과제를 읽게 하면, 과제 정의 자체가 팀의 자산으로 남는다.

## 5. 검토와 병합

에이전트 PR의 검토는 사람 PR의 검토와 초점이 다르다.

- **의도 대비 결과를 본다**: 코드 스타일은 린트가 잡았고 테스트는 통과했다. 검토자가 볼 것은 "과제가 요구한 것을 했는가, 요구하지 않은 것을 하지 않았는가"다. 에이전트는 요청 밖의 "개선"을 끼워 넣는 경향이 있다.
- **테스트를 먼저 읽는다**: 에이전트가 테스트를 통과시키기 위해 테스트를 약화시켰는지(단언 삭제, 예외 무시, 스킵 추가) 확인한다. 이는 에이전트 PR의 대표적 실패 패턴이다.
- **데이터 영향을 확인한다**: 피처·스키마·SQL 변경은 다운스트림 영향을 사람이 판단해야 한다. 계약 검사가 통과했더라도 의미 변경(단위, 정의)은 기계가 잡지 못한다.
- **PR 크기를 제한한다**: 에이전트는 큰 PR을 쉽게 만든다. 변경 파일 수·줄 수 상한을 두고, 넘으면 분할을 요구한다. 검토 가능한 크기가 곧 안전한 크기다.
- **에이전트 리뷰를 1차로 둔다**: 별도 에이전트(또는 같은 도구의 리뷰 모드)가 PR을 먼저 검토해 명백한 문제를 잡고, 사람은 2차로 의도·영향을 본다. 작성 에이전트와 리뷰 에이전트의 프롬프트는 달라야 한다.
- **커밋에 출처를 남긴다**: 에이전트가 작성한 커밋은 공동 작성자(Co-Authored-By)나 트레일러로 표시한다. 사후 분석에서 에이전트 코드의 결함률을 추적하는 근거가 된다.

**CI 파이프라인 변경**

책 7.4.1의 CI 파이프라인에 다음이 추가된다.

```
PR 생성 (사람 또는 에이전트)
   │
   ▼
[자동 검사] 린트 → 단위 테스트 → 데이터 검증(샘플) → 계약 검사 → 드라이런 → 비용 추정
   │
   ▼
[에이전트 1차 리뷰] 의도 대비 변경 범위, 테스트 약화 여부, 보안 패턴
   │
   ▼
[사람 2차 리뷰] 도메인 영향, 의미 변경, 승인
   │
   ▼
[병합 → 스테이징 배포 → 실데이터 검증 → 운영]
```

<br>

## 6. 팀 운영

- **컨텍스트 파일의 소유자를 정한다**: 규칙이 바뀌면 컨텍스트 파일을 갱신하는 사람이 있어야 한다. PR 검토에서 반복 지적되는 사항은 컨텍스트 파일에 규칙으로 추가한다. 이 순환이 팀의 암묵지를 명시지로 바꾸는 부수 효과를 낸다.
- **에이전트 실패를 기록한다**: 에이전트가 틀린 방향으로 간 사례(잘못된 가정, 컨텍스트 부족, 검증 부재)를 모아 원인을 분류한다. 대부분 저장소의 문서·테스트 부족으로 귀결되며, 그 개선이 사람에게도 이롭다.
- **비용을 본다**: 도구 사용 비용은 계정 단위로 측정하고, 과제 유형별 소요 토큰을 파악해 어떤 작업이 비용 대비 효과가 큰지 판단한다.
- **역량 재배치**: 코드 작성 시간이 줄면 그 시간은 과제 정의·검토·데이터 이해에 쓰여야 한다. 팀 리더는 "PR 수"가 아니라 "검증된 변경의 품질"과 "과제 정의의 명확성"으로 팀을 본다.
- **신입·주니어 육성**: 에이전트가 보일러플레이트를 대신하면 주니어가 기본기를 익힐 기회가 줄어든다. 코드 리뷰 참여, 에이전트 결과의 검증 담당, 컨텍스트 파일 작성을 통해 저장소를 깊이 이해하는 경로를 의도적으로 만든다.

<br>
<br>

에이전트 코딩 도구를 데이터·ML 팀에 도입하는 일은 도구 설치가 아니라 **저장소와 프로세스를 "설명 가능하고 검증 가능하게" 만드는 일**이다. 컨텍스트 파일, 계약, 샘플 데이터, 빠른 검증 명령, 격리된 실행 환경, 의도 중심 검토. 이것들은 모두 에이전트 이전에도 좋은 관행이었지만, 이제는 생산성의 전제 조건이 되었다. 에이전트는 잘 정비된 저장소에서는 팀의 배수(multiplier)가 되고, 정비되지 않은 저장소에서는 검토 부담만 늘리는 소음이 된다.
