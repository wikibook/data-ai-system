# 텍스트-투-SQL과 시맨틱 레이어

"지난달 신규 가입자의 첫 구매 전환율이 어떻게 됐어?"라는 질문에 LLM이 SQL을 작성해 웨어하우스에 직접 질의하는 **데이터 에이전트**가 빠르게 보편화되었다. 책 1.2(데이터 분석)와 6.2(데이터 아키텍처 패턴)가 다룬 분석과 저장 구조 위에, 이제 "자연어로 질문하는 사용자"라는 새로운 소비자가 올라온 것이다. 그런데 텍스트-투-SQL(Text-to-SQL)의 실무 정확도는 벤치마크 점수와 다르다. 모델이 SQL 문법을 틀리는 경우는 드물고, 대부분의 오답은 **"신규 가입자"가 무엇이고 "전환율"을 어떻게 계산하는지를 조직과 다르게 해석**하는 데서 나온다. 이 문서는 그 문제의 해법으로 자리 잡은 시맨틱 레이어(semantic layer)와, 텍스트-투-SQL 시스템을 신뢰할 수 있게 만드는 설계를 정리한다.

<br>

## 1. 텍스트-투-SQL이 실패하는 지점

| 실패 유형 | 예 | 원인 |
| --- | --- | --- |
| **지표 정의 불일치** | "매출"을 취소·환불 제외 전 금액으로 계산 | 조직의 지표 정의가 SQL 어디에도 명시되지 않음 |
| **테이블 선택 오류** | `orders`와 `orders_v2`, `orders_daily_agg` 중 잘못된 것을 선택 | 유사 이름 테이블, 폐기 테이블 잔존, 설명 부재 |
| **조인 오류** | 1:N 관계를 조인해 금액이 중복 집계됨 | 관계·카디널리티 정보 부재 |
| **필터 누락** | 테스트 계정, 삭제 플래그, 내부 직원을 제외하지 않음 | "당연한" 필터가 문서화되지 않음 |
| **시간 처리 오류** | UTC/KST 혼동, 주문일 vs 결제일 vs 배송일 | 시간 컬럼의 의미와 시간대가 불명확 |
| **권한 위반** | 접근하면 안 되는 개인정보 컬럼 조회 | 모델이 권한을 알지 못하고, 실행 계정이 과도한 권한을 가짐 |
| **비용 폭주** | 파티션 필터 없이 수 년치 이벤트 테이블 전체 스캔 | 파티션 키·비용 정보 부재 |

이 표에서 SQL 문법 오류가 없다는 점이 중요하다. 실패의 원인은 모델이 아니라 **모델이 볼 수 있는 정보에 조직의 지식이 없다는 것**이다. 스키마(컬럼 이름과 타입)만 주면 모델은 컬럼 이름으로 의미를 추측하고, 그 추측은 조직마다 다른 정의와 어긋난다.

<br>

## 2. 시맨틱 레이어: 정의를 한곳에 두기

시맨틱 레이어는 물리 테이블 위에 **비즈니스 개념(엔티티, 차원, 지표)과 그 계산 방식을 선언적으로 정의한 계층**이다. BI 도구의 데이터 모델(LookML 등)이 원형이며, 최근에는 dbt Semantic Layer(MetricFlow), Cube, Databricks Metric Views, Snowflake Semantic Views, AtScale 같은 독립 계층으로 표준화되고 있다.

```yaml
# 시맨틱 모델 예시 (개념적 표기)
semantic_model: orders
  table: analytics.fct_orders
  description: "결제 완료된 주문. 테스트 계정과 내부 직원 주문은 이미 제외됨."
  entities:
    - name: order_id     type: primary
    - name: customer_id  type: foreign   references: customers
  dimensions:
    - name: ordered_at   type: time   granularity: day   timezone: Asia/Seoul
      description: "결제 완료 시각. 배송·환불 시각과 다름."
    - name: category     type: categorical
  measures:
    - name: gross_revenue   expr: amount_krw                          agg: sum
    - name: net_revenue     expr: amount_krw - refund_amount_krw      agg: sum
      description: "환불 반영 순매출. 대시보드의 '매출'은 이 지표를 사용."
    - name: order_count     expr: order_id                            agg: count_distinct

metrics:
  - name: first_purchase_conversion_rate
    description: "가입 후 30일 내 첫 구매한 신규 가입자 비율. 신규 가입자 = signup_at 기준 해당 월 가입."
    type: ratio
    numerator: first_purchasers_30d
    denominator: new_signups
```

**시맨틱 레이어가 텍스트-투-SQL에 주는 것**

- **정의의 단일 출처**: "순매출"이 무엇인지 한곳에만 있다. 모델은 SQL 대신 `query(metrics=[net_revenue], dimensions=[category], time=last_month)` 형태의 **지표 질의**를 생성하고, 시맨틱 레이어가 이를 올바른 SQL로 컴파일한다. 조인·필터·집계 로직이 모델의 손을 떠난다.
- **탐색 공간 축소**: 모델이 고를 것은 수천 개 컬럼이 아니라 수십 개의 지표·차원이다. 선택 정확도가 크게 오른다.
- **설명이 곧 컨텍스트**: 지표·차원의 `description`이 모델에게 주입되는 문서가 된다. 시맨틱 레이어를 잘 문서화하는 일이 곧 텍스트-투-SQL 정확도를 올리는 일이다.
- **사람과 같은 답**: 대시보드와 에이전트가 같은 정의를 쓰므로 "대시보드에는 3.2%인데 에이전트는 3.5%라고 한다"는 신뢰 붕괴가 사라진다.

시맨틱 레이어가 없다면 데이터 에이전트 도입 전에 먼저 만들어야 한다. 핵심 지표 20~30개와 주요 차원부터 시작하면 된다. 이 작업은 에이전트가 없어도 조직에 가치가 있으며(지표 정의 표준화), 에이전트는 그 위에서 정확도를 얻는다.

## 3. 시스템 구조

```
사용자 질문
   │
   ▼
[의도 분류·라우팅] ─ 지표 질의인가 / 임의 SQL이 필요한가 / 답할 수 없는 질문인가
   │
   ▼
[컨텍스트 조립]
   ├─ 시맨틱 레이어에서 관련 지표·차원 검색 (임베딩 + 키워드)
   ├─ 지표 정의·설명·예시 질의 주입
   ├─ 필요 시 관련 테이블 스키마·샘플 값 주입
   └─ 사용자 권한 정보 주입 (접근 가능한 데이터 범위)
   │
   ▼
[생성] ─ 1순위: 지표 질의(시맨틱 레이어 API)  2순위: 제약된 SQL
   │
   ▼
[검증] ─ 구문 검사 → 권한 검사 → 비용 추정 → 드라이런 → (임의 SQL이면) 자기 검토
   │
   ▼
[실행] ─ 읽기 전용, 행·시간·비용 상한, 사용자 신원으로 실행
   │
   ▼
[응답] ─ 결과 표 + 사용한 지표 정의 + 실행된 SQL + 가정 명시
```

### 3.1 컨텍스트 조립

스키마 전체를 프롬프트에 넣는 방식은 테이블이 수백 개를 넘으면 동작하지 않는다. 질문과 관련된 부분만 검색해 넣는다.

- **스키마 링킹**: 질문을 임베딩해 관련 지표·차원·테이블을 검색한다. 테이블·컬럼 설명, 과거 질의 이력, 동의어 사전(사용자가 "고객"이라 부르는 것이 `customer`인지 `user`인지)을 함께 색인한다.
- **샘플 값**: 카테고리형 컬럼의 실제 값 몇 개(`category: 'TOP', 'BOTTOM', 'OUTER', ...`)를 넣어 모델이 필터 값을 지어내지 않게 한다. 개인정보 컬럼은 제외한다.
- **예시 질의(few-shot)**: 검증된 "질문 → 지표 질의/SQL" 쌍을 질문 유사도로 검색해 3~5개 넣는다. 이 예시 저장소가 정확도를 가장 크게 올리는 자산이며, 사람이 검증한 질의를 계속 추가해 키운다.
- **권한 정보**: 사용자가 볼 수 있는 데이터 범위(부서, 지역, 컬럼)를 명시해 모델이 처음부터 범위 안에서 생성하게 한다. 물론 실행 단계에서도 강제한다.

### 3.2 생성 전략

- **지표 질의 우선**: 질문이 정의된 지표·차원으로 표현되면 SQL을 생성하지 않고 시맨틱 레이어 API를 호출한다. 정확도·안전성·비용 모두 우월하다.
- **제약된 SQL은 예외 경로**: 시맨틱 레이어에 없는 질문(임시 탐색, 새 조합)에만 SQL 생성을 허용하고, 허용 테이블·컬럼 목록을 프롬프트와 검증 단계 양쪽에서 제한한다.
- **답할 수 없음을 허용**: 정의되지 않은 지표를 묻거나 데이터가 없는 질문에는 "해당 지표는 정의되어 있지 않습니다. 가까운 지표는 X입니다"라고 답하게 한다. 억지로 SQL을 만들어 그럴듯한 숫자를 내는 것이 최악의 실패다.
- **가정 명시**: "신규 가입자를 '해당 월 가입' 기준으로, 전환은 '가입 후 30일 내 첫 결제'로 해석했습니다"처럼 해석을 응답에 포함한다. 사용자가 해석 오류를 발견할 수 있는 유일한 방법이다.

### 3.3 검증과 실행

- **구문·의미 검사**: 파서(sqlglot 등)로 구문을 검사하고, 참조 테이블·컬럼이 허용 목록에 있는지, `SELECT` 외 문장이 없는지 확인한다.
- **비용 추정**: `EXPLAIN`이나 웨어하우스의 드라이런 모드로 스캔 바이트·예상 비용을 확인하고 상한을 넘으면 실행하지 않는다. 파티션 필터가 없는 대형 테이블 조회는 자동으로 기간 필터를 요구한다.
- **실행 제약**: 읽기 전용 역할, 행 수 상한(예: 1,000행), 실행 시간 상한(예: 30초), 사용자 신원으로 실행(행 수준 보안 적용). 서비스 계정 하나로 실행하는 구조는 권한 위반의 근본 원인이므로 피한다.
- **결과 자기 검토**: 임의 SQL 경로에서는 실행 결과를 모델에게 다시 보여 "질문에 맞는 결과인가, 중복 집계 징후(비정상적으로 큰 값)가 있는가"를 확인하게 하고, 의심되면 사용자에게 알린다.

## 4. 시맨틱 레이어 도구 비교

| 도구 | 성격 | 특징 |
| --- | --- | --- |
| **dbt Semantic Layer (MetricFlow)** | dbt 프로젝트 안에서 지표 정의 | dbt 모델과 같은 저장소·리뷰 절차, 다양한 BI·API 연동, 웨어하우스 중립 |
| **Cube** | 독립 시맨틱 레이어 서버 | 캐싱·사전 집계 내장, REST/GraphQL/SQL API, 접근 제어 내장, AI 에이전트용 API 제공 |
| **Databricks Metric Views / Unity Catalog** | 플랫폼 내장 | 카탈로그·권한·계보와 통합, Genie 등 플랫폼 AI 기능이 직접 사용 |
| **Snowflake Semantic Views** | 플랫폼 내장 | Cortex Analyst가 직접 사용, 웨어하우스 권한 모델 상속 |
| **LookML (Looker)** | BI 내장 | 가장 성숙한 모델링 언어, Looker 생태계 종속 |

선택 기준은 "조직의 정의를 어디에서 관리하는가"다. 이미 dbt로 변환을 관리한다면 dbt Semantic Layer가 자연스럽고, 여러 BI·에이전트가 같은 정의를 써야 하고 캐싱이 중요하면 Cube 같은 독립 계층이 유리하며, 단일 플랫폼(Databricks, Snowflake)에 집중되어 있다면 내장 기능이 권한·계보 통합에서 앞선다. 어느 쪽이든 **정의를 코드로 버전 관리하고 리뷰를 거치는 것**이 도구 선택보다 중요하다.

## 5. 평가와 운영

- **평가 세트**: 사람이 검증한 "질문 → 정답 SQL(또는 지표 질의) → 정답 결과" 쌍을 100~300개 만든다. 정확도는 SQL 문자열 일치가 아니라 **실행 결과 일치**(execution accuracy)로 측정한다. 같은 답을 내는 다른 SQL은 정답이다. 카테고리(단순 집계, 조인, 시간 비교, 정의되지 않은 지표)별로 나눠 본다.
- **모호성 처리 평가**: 의도적으로 모호한 질문("매출 얼마야?" — 기간·정의 미지정)을 넣고, 되묻거나 가정을 명시하는지 확인한다.
- **운영 신호**: 실행 실패율, 비용 상한 차단율, 사용자 수정 요청률("아니 환불 제외한 거"), 같은 질문 재시도율. 실패 질의는 검토 큐로 보내 예시 저장소와 시맨틱 레이어 보강에 사용한다.
- **정의 변경 관리**: 지표 정의가 바뀌면 과거 질의의 결과가 달라진다. 정의 변경은 [데이터 계약과 스키마 진화](./data-contracts-schema-evolution.md)와 같은 절차(리뷰, 버전, 공지)를 거치고, 응답에 사용한 정의 버전을 남긴다.
- **MCP로 노출**: 시맨틱 레이어를 `list_metrics`, `query_metric` 도구로 노출하면 여러 에이전트가 같은 정의를 쓴다. [MCP 서버 설계와 운영 실무](./mcp-server-design.md) 6절을 참고한다.

평가 하네스 구축은 [RAG·LLM 평가 데이터세트 구축과 오프라인 평가 하네스](./llm-evaluation-harness.md)의 방법을 따르되, 채점기를 "실행 결과 비교"로 바꾸면 된다.

<br>
<br>

텍스트-투-SQL의 정확도 문제는 모델 문제로 보이지만 실제로는 **데이터 거버넌스 문제**다. 지표 정의가 사람마다 다른 조직에서는 사람도 틀린 SQL을 쓴다. 시맨틱 레이어는 그 정의를 한곳에 모아 사람과 모델이 같은 답을 내게 하는 장치이며, 데이터 에이전트는 이 장치가 있을 때만 신뢰를 얻는다. 책 5.3의 데이터 거버넌스가 "있으면 좋은 것"에서 "에이전트 시대의 전제 조건"으로 바뀐 대표적인 사례다.
