# RAG·LLM 평가 데이터세트 구축과 오프라인 평가 하네스

LLM 애플리케이션은 프롬프트 한 줄, 임베딩 모델 교체, 청크 크기 변경만으로도 응답 품질이 크게 흔들린다. 그런데 정답이 하나로 정해지지 않는 생성 과제의 특성 때문에 "좋아졌는지"를 감으로 판단하기 쉽고, 그 결과 한 곳을 고치면 다른 곳이 조용히 나빠지는 회귀(regression)가 반복된다. 책 12.4.3(RAG 시스템 성능 평가 및 개선 전략)은 어떤 지표로 무엇을 측정할지를 정리했다. 이 문서는 그 지표를 **반복 가능하게 측정하는 장치**, 즉 평가 데이터세트와 오프라인 평가 하네스를 어떻게 구축하고 운영하는지를 다룬다.

[RAG 품질 저하 요인과 대응 전략](./rag-quality-risks.md)이 "어디가 나빠질 수 있는가"를 다룬다면, 이 문서는 "나빠졌음을 어떻게 자동으로 알아내는가"를 다룬다.

<br>

## 1. 왜 오프라인 평가 하네스가 필요한가

A/B 테스트와 실사용 로그는 최종 판단 기준이지만, 트래픽이 필요하고 결과를 얻기까지 며칠이 걸리며 나쁜 변경이 사용자에게 노출된다. 오프라인 평가 하네스는 그 앞단에서 다음 역할을 한다.

- **회귀 방지**: 프롬프트·모델·검색 설정을 바꿀 때마다 고정된 평가 세트로 점수를 산출하고, 기준선보다 떨어지면 배포를 막는다. 소프트웨어의 단위 테스트와 같은 위치다.
- **변경 간 비교**: 여러 임베딩 모델, 청크 전략, 리랭커 조합을 같은 기준으로 비교해 의사결정을 수치화한다.
- **실패 사례 축적**: 운영 중 발견된 오답을 평가 세트에 추가해 같은 실패가 재발하지 않도록 한다.

하네스는 크게 **평가 데이터세트**, **실행기(파이프라인을 호출해 응답을 수집)**, **채점기(지표 계산)**, **리포트(기준선 비교와 알림)** 네 부분으로 구성된다.

<br>

## 2. 평가 데이터세트 구축

### 2.1 데이터세트의 구성 단위

RAG 시스템의 평가 항목 하나는 최소한 다음 필드를 갖는다.

```
{
  "id": "faq-0132",
  "question": "환불 신청 후 카드 취소까지 며칠이 걸리나요?",
  "ground_truth_answer": "카드사 정책에 따라 영업일 기준 3~7일이 소요된다.",
  "relevant_doc_ids": ["policy/refund#section-3"],
  "metadata": {"category": "refund", "difficulty": "easy", "source": "cs-log-2025-06"}
}
```

`relevant_doc_ids`가 있으면 검색 단계를 독립적으로 평가할 수 있고, `ground_truth_answer`가 있으면 생성 단계의 정확성을 평가할 수 있다. 둘 다 없는 항목도 유용하다. 답의 근거가 검색 문서 안에 있는지(faithfulness)는 정답 없이도 측정할 수 있기 때문이다.

### 2.2 질의를 어디서 얻는가

| 출처 | 장점 | 단점 | 활용 |
| --- | --- | --- | --- |
| **실사용 로그** | 실제 분포를 반영, 실패 사례 포함 | 정답 라벨링 비용, 개인정보 처리 필요 | 핵심 세트의 근간. 마스킹 후 샘플링 |
| **도메인 전문가 작성** | 품질 높음, 경계 사례 포함 가능 | 비용 크고 수량 적음 | 고난도·고위험 질의 |
| **합성 생성(synthetic)** | 대량 생성 가능, 문서별로 균일한 커버리지 | 실제 사용자 질의와 표현이 다름, 너무 쉬운 질의 편향 | 초기 부트스트랩, 문서 커버리지 확보 |
| **레드팀 세트** | 인젠션·유해 요청·범위 밖 질의 | 정상 성능과 별도 관리 필요 | 안전성 회귀 방지 |

**합성 질의 생성 절차**

1. 문서 청크를 샘플링하고 LLM에게 "이 청크로만 답할 수 있는 질문과 정답을 만들어 달라"고 요청한다. 생성된 항목은 `relevant_doc_ids`가 자동으로 확정된다.
2. 질문 유형을 명시적으로 다양화한다. 단일 사실 조회, 여러 청크를 종합해야 하는 질문(multi-hop), 비교 질문, 문서에 답이 없는 질문(unanswerable), 오탈자·구어체 변형을 각각 일정 비율로 배치한다.
3. 생성 결과를 사람 또는 별도 LLM이 검수해 "청크 없이도 답할 수 있는 질문", "답이 청크와 불일치하는 항목"을 제거한다.
4. 실사용 로그가 쌓이면 합성 항목의 비율을 점차 낮춘다.

### 2.3 규모와 구성

- 회귀 감지 목적이라면 **200~500개** 정도에서 통계적으로 의미 있는 차이를 잡을 수 있다. 수천 개 세트는 실행 비용이 커서 오히려 자주 돌리지 않게 된다.
- 항목마다 **카테고리·난이도·질문 유형** 메타데이터를 붙여, 전체 점수뿐 아니라 세그먼트별 점수를 본다. 전체 평균이 유지되더라도 특정 카테고리가 무너지는 경우가 흔하다.
- **정답이 없는 질문**을 10~20% 포함한다. RAG의 대표적 실패인 "모르는데 아는 척 답하는" 행동을 잡는 유일한 방법이다.
- 세트를 **핵심(core)·확장(extended)·안전(safety)** 세 층으로 나눠, 핵심은 매 변경마다, 확장은 야간 배치, 안전은 프롬프트·모델 변경 시 실행하는 식으로 비용을 조절한다.

### 2.4 데이터세트 자체를 버전 관리한다

평가 세트는 코드와 같은 저장소에서 버전 관리하고, 변경 시 리뷰를 거친다. 세트가 바뀌면 점수의 기준선도 바뀌므로, 세트 버전과 점수를 항상 함께 기록한다. 운영 중 발견된 실패 사례를 추가할 때는 "어떤 배포에서 어떤 오답이 났는가"를 메타데이터에 남겨 추적할 수 있게 한다.

## 3. 지표 계층과 채점 방식

책 표 12.3의 분류를 따라 검색·생성·운영 세 층으로 나누고, 각 층에서 **결정적 지표를 먼저, LLM 판정을 보조로** 사용한다.

### 3.1 검색 단계 (결정적 지표)

`relevant_doc_ids`가 있으면 코드로 계산할 수 있어 비용이 없고 재현성이 완벽하다.

| 지표 | 의미 | 사용 |
| --- | --- | --- |
| Recall@k | 정답 문서가 상위 k개에 포함된 비율 | 리랭커 이전 후보 생성 품질. k는 실제 LLM에 넘기는 문서 수로 설정 |
| MRR | 첫 정답 문서 순위의 역수 평균 | 상위 노출 품질 |
| NDCG@k | 순위 가중 관련성 | 부분 관련 문서가 있을 때 |
| Hit rate | 정답 문서가 하나라도 포함된 비율 | 가장 단순한 회귀 신호 |

검색 지표가 유지되는데 최종 답변이 나빠졌다면 원인은 생성 단계에 있고, 검색 지표가 함께 떨어졌다면 임베딩·청킹·인덱스를 먼저 본다. 이 분리가 가능하다는 것이 검색 라벨을 유지하는 가장 큰 이유다.

### 3.2 생성 단계 (LLM-as-a-Judge 중심)

생성 응답은 표현이 다양해 문자열 일치나 BLEU·ROUGE로는 품질을 제대로 잡지 못한다. LLM에게 채점 기준을 주고 판정하게 하는 방식이 표준이 되었으며, 대표적인 평가 축은 다음과 같다.

| 축 | 질문 | 필요한 입력 |
| --- | --- | --- |
| **Faithfulness(근거 일치)** | 답변의 각 주장이 검색된 문서로 뒷받침되는가 | 답변 + 검색 문서 |
| **Answer correctness(정확성)** | 답변이 정답과 의미상 일치하는가 | 답변 + 정답 |
| **Answer relevance(관련성)** | 답변이 질문에 실제로 응답하는가 | 답변 + 질문 |
| **Context relevance(문맥 관련성)** | 검색된 문서가 질문과 관련 있는가 | 질문 + 검색 문서 |
| **Refusal correctness** | 답이 없는 질문에 올바르게 모른다고 했는가 | 답변 + unanswerable 플래그 |

**LLM 판정의 신뢰도를 높이는 방법**

- **채점 기준(rubric)을 구체적으로 쓴다**: "1~5점으로 평가하라"보다 "각 문장을 주장 단위로 나누고, 문서에서 근거를 찾을 수 있는 주장의 비율을 계산하라"처럼 절차를 지시한다. 점수보다 이진 판정(통과/실패)이 일관성이 높다.
- **쌍대 비교(pairwise)를 활용한다**: 두 응답 중 어느 쪽이 나은지를 묻는 방식이 절대 점수보다 안정적이다. 변경 전후 비교에 적합하며, 위치 편향을 막기 위해 순서를 바꿔 두 번 묻는다.
- **판정 모델을 피평가 모델과 다르게 한다**: 같은 모델은 자기 출력을 선호하는 경향(self-preference bias)이 있다.
- **사람 라벨과의 일치도를 측정한다**: 100~200개 항목에 사람 라벨을 만들고, 판정 모델의 일치도(Cohen's kappa 등)를 확인한다. 일치도가 낮은 축은 기준을 다시 쓰거나 사람 평가로 대체한다.
- **판정 프롬프트도 버전 관리한다**: 판정 프롬프트가 바뀌면 점수 척도가 바뀐다. 기준선을 다시 잡아야 한다.

### 3.3 운영 지표

지연 시간(TTFT, E2E), 토큰 사용량, 비용, 도구 호출 횟수를 평가 실행 시 함께 기록한다. 품질이 1% 오르는 대신 비용이 2배가 되는 변경을 걸러내는 데 필요하다.

## 4. 하네스 구조와 실행 흐름

```
[평가 세트 v12]
   │
   ▼
[실행기] ─ 파이프라인 호출 → 응답·검색 문서·지연·토큰 수집
   │
   ▼
[채점기]
   ├─ 검색 지표 (코드: Recall@k, MRR, NDCG)
   ├─ 생성 지표 (LLM 판정, 결과 캐시)
   ├─ 운영 지표 (지연, 토큰, 비용)
   │
   ▼
[리포트] ─ 기준선 대비 변화량, 세그먼트별 점수, 새로 실패한 항목 목록
   │
   ├─ 통과 → 배포
   └─ 실패 → 차단·알림
```
<br>

**설계 시 고려사항**

- **파이프라인을 단계별로 호출할 수 있게 만든다**: 검색만 실행, 주어진 문서로 생성만 실행이 가능해야 단계별 평가와 원인 분리가 된다. 이는 서비스 코드의 모듈화 문제이기도 하다.
- **결정성 확보**: temperature를 0으로 두고, 그래도 남는 변동을 감안해 같은 세트를 2~3회 실행한 평균과 분산을 본다. 분산이 크면 지표 자체가 불안정하다는 신호다.
- **판정 결과 캐싱**: 동일한 (질문, 응답, 문서, 판정 프롬프트 버전) 조합의 판정은 재사용한다. 판정 비용이 하네스 비용의 대부분을 차지하므로 캐시 적중률이 실행 빈도를 결정한다.
- **실패 사례를 사람이 보기 쉽게 출력한다**: 점수표보다 "이번 변경으로 새로 실패한 항목 12개"의 질문·응답·근거 문서를 나열한 리포트가 디버깅에 훨씬 유용하다.
- **CI 통합**: 프롬프트·검색 설정·모델 버전을 담은 파일이 바뀌면 핵심 세트를 자동 실행하고, 기준 지표(예: faithfulness 통과율, Recall@5)가 임곗값 아래로 떨어지면 병합을 차단한다. 책 7.4의 CI/CD 파이프라인에 평가 단계를 추가하는 것이다.

<br>

## 5. 온라인 평가와의 연결

오프라인 하네스는 온라인 신호로 보정되어야 한다.

- **트레이싱**: 운영 환경에서 요청별로 프롬프트 버전, 검색 문서 ID, 응답, 지연, 토큰, 사용자 피드백(좋아요/싫어요, 재질문)을 하나의 트레이스로 남긴다. Langfuse, LangSmith, Arize Phoenix, OpenTelemetry 기반 자체 구축 등이 사용된다. 트레이스 구조와 운영 지표 설계는 [에이전트 관측성과 운영(AgentOps)](./agent-observability-operations.md)에서 상세히 다룬다.
- **샘플링 판정**: 운영 트래픽의 일부(예: 1%)에 오프라인과 동일한 LLM 판정을 비동기로 적용해 품질 추세를 추적한다. 오프라인 점수와 온라인 점수가 벌어지면 평가 세트가 실제 분포와 멀어졌다는 뜻이다.
- **실패 사례 환류**: 사용자가 부정 피드백을 남긴 항목, 판정 점수가 낮은 항목을 검수 큐에 넣고, 확인된 것은 평가 세트에 추가한다. 이 순환이 돌아야 평가 세트가 살아 있는 자산이 된다.
- **A/B 테스트는 최종 관문**: 오프라인에서 개선이 확인된 변경만 A/B로 보낸다. 책 9.4의 실험 설계 원칙이 그대로 적용되며, 지표는 CTR·만족도·재질문율 같은 사용자 행동 지표를 쓴다.

## 6. 도구

| 도구 | 성격 | 특징 |
| --- | --- | --- |
| **Ragas** | RAG 평가 라이브러리 | faithfulness·answer relevance·context precision 등 표준 지표, 합성 테스트셋 생성 |
| **DeepEval** | LLM 평가 프레임워크 | pytest 스타일 테스트 작성, 다양한 판정 지표, CI 통합 용이 |
| **promptfoo** | 프롬프트 평가·레드팀 CLI | 설정 파일 기반, 여러 모델·프롬프트 매트릭스 비교, 인젠션 공격 세트 내장 |
| **OpenAI Evals / lm-evaluation-harness** | 벤치마크 실행 프레임워크 | 공개 벤치마크 실행, 커스텀 평가 추가 |
| **Langfuse / LangSmith / Phoenix** | 트레이싱·관측 플랫폼 | 운영 트레이스 수집, 데이터세트 관리, 온라인 판정 |
| **MLflow LLM Evaluate** | 실험 추적 통합 | 기존 MLflow 실험 관리와 LLM 평가 결과를 한곳에서 관리 |

도구는 하네스의 채점기와 리포트 부분을 빠르게 갖추게 해 주지만, 평가 세트의 품질과 판정 기준의 도메인 적합성은 도구가 해결해 주지 않는다. 초기에는 도구를 그대로 쓰되, 도메인 고유의 판정 기준(예: "환불 정책 답변은 반드시 소요 기간을 영업일 기준으로 명시해야 한다")은 직접 작성해 추가하는 것이 일반적이다.

<br>
<br>

평가 하네스의 가치는 지표의 정교함이 아니라 **매 변경마다 빠짐없이 실행된다는 규칙성**에서 나온다. 완벽한 세트를 만들려다 시작을 미루는 것보다, 100개 항목과 두 개 지표로 시작해 실패 사례를 쌓아가며 키우는 편이 낫다. 평가 세트가 곧 그 서비스가 "무엇을 잘해야 하는가"에 대한 팀의 합의를 담은 문서가 되기 때문이다.
