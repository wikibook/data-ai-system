# 소형 언어 모델(SLM)과 온디바이스·엣지 추론

책 12.2.2·12.2.3은 GPT, LLaMA, Claude 같은 대형 모델을 비교하고 선택 기준을 제시했다. 그 뒤로 일어난 큰 변화 중 하나는 **3B~8B급 소형 언어 모델(Small Language Model, SLM)의 품질이 특정 과제에서 대형 모델에 근접**했다는 것이다. 분류·추출·라우팅·요약·형식 변환처럼 범위가 정해진 과제에서는 자체 호스팅 SLM이 대형 API 호출을 대체하는 것이 비용 최적화의 기본 수단이 되었고, 같은 모델이 노트북·스마트폰·엣지 장비에서도 돌아가면서 온디바이스 추론이 실무 선택지가 되었다. 이 문서는 SLM을 어디에 어떻게 쓰고, 대형 모델과 어떻게 조합하는지를 정리한다.

<br>

## 1. SLM이 대형 모델을 대체하는 조건

SLM은 대형 모델의 축소판이 아니다. 지식의 폭과 복잡한 다단계 추론은 뚜렷하게 열세지만, **과제가 좁고 입력 형식이 안정적이며 출력이 구조화될 수 있는 경우** 격차가 크게 줄어든다. 판단 기준은 다음과 같다.

| 조건 | SLM 적합 | 대형 모델 필요 |
| --- | --- | --- |
| 과제 범위 | 하나의 좁은 과제(의도 분류, 개체 추출, 감성, 라우팅, 정해진 형식의 요약) | 개방형 대화, 다영역 질의응답 |
| 필요한 지식 | 입력 안에 있음(문서 요약, 컨텍스트 기반 QA) | 모델의 세계 지식에 의존 |
| 추론 깊이 | 1~2단계 | 계획·다단계 추론·도구 조합 |
| 출력 형식 | JSON·라벨·짧은 텍스트 | 긴 자유 서술 |
| 평가 데이터 | 있음(미세 조정·검증 가능) | 없음 |
| 호출량 | 많음(비용 절감 효과 큼) | 적음 |
| 지연·프라이버시 요구 | 엄격함(온디바이스, 실시간) | 관대함 |

이 기준에 맞는 과제는 실무 LLM 워크로드의 상당 부분을 차지한다. 사용자 문의 분류, 리뷰에서 속성 추출, 상품명 정규화, 검색 질의 재작성, 로그 메시지 분류, 에이전트 내부의 라우팅·도구 인자 추출이 모두 해당한다.

**대표 모델군(2026년 기준)**: Llama 3.x 3B/8B, Qwen 2.5/3 계열 0.5B~14B, Gemma 3 1B~12B, Phi-4 계열, Mistral Small, SmolLM, 한국어 특화로는 EXAONE·HyperCLOVA X SEED·kanana 등. 모델 이름은 빠르게 바뀌므로 특정 모델보다 "동급 크기에서 자사 과제 평가 세트로 비교한다"는 절차를 갖추는 것이 중요하다.

<br>

## 2. 과제별 모델 계층화

가장 효과적인 구조는 SLM 하나로 전부 대체하는 것이 아니라 **과제 난이도에 따라 모델을 계층화**하는 것이다.

```
요청
 │
 ▼
[1계층: 규칙·캐시] ─ 정규식, 정확 일치, 이전 결과 캐시 → 비용 0
 │  미해결
 ▼
[2계층: SLM (자체 호스팅, 1~8B)] ─ 분류·추출·라우팅·단순 응답 → 저비용, 저지연
 │  신뢰도 낮음 / 복잡 과제로 판정
 ▼
[3계층: 중형 모델 또는 대형 API] ─ 다단계 추론, 개방형 생성, 에이전트 → 고비용
 │
 ▼
응답  (+ 각 계층의 판정·비용 기록)
```

- **라우팅 기준**: SLM이 자기 출력의 신뢰도(로그 확률, 별도 분류 헤드, "불확실" 라벨)를 함께 내게 하고, 임곗값 아래면 상위 계층으로 넘긴다. 임곗값은 평가 세트에서 "상위 계층으로 넘겼을 때 정확도 상승 대비 비용 증가"로 조정한다.
- **캐스케이드 vs 라우터**: 캐스케이드는 SLM을 먼저 실행하고 실패 시 상위로 가므로 지연이 누적된다. 라우터는 소형 분류기가 처음부터 계층을 고르므로 지연은 짧지만 라우터 자체의 오분류가 생긴다. 지연이 중요하면 라우터, 정확도가 중요하면 캐스케이드다.
- **비용 효과**: 전체 요청의 60~80%가 1·2계층에서 끝나면 대형 API 비용은 그만큼 줄어든다. 단, SLM 서빙 인프라의 고정비(GPU 상시 구동)가 있으므로 호출량이 일정 규모 이상일 때 손익분기를 넘는다. [모델 서빙 시 트레이드오프 고려사항](./model-serving-tradeoffs.md) 5절의 비용 지표로 계산한다.

에이전트 내부에서도 같은 원리가 적용된다. 계획·최종 응답은 대형 모델, 도구 인자 추출·결과 요약·라우팅은 SLM으로 나누면 에이전트 비용의 상당 부분을 줄일 수 있다([LLM 에이전트와 도구 호출 아키텍처](./llm-agent-architecture.md) 6절).

## 3. SLM을 과제에 맞추는 방법

범용 SLM을 그대로 쓰는 것과 과제에 맞춘 것의 격차는 대형 모델보다 훨씬 크다. 책 12.3.1의 프롬프트·컨텍스트·미세 조정 비교가 SLM에서는 미세 조정 쪽으로 기운다.

| 방법 | 비용 | 효과 | 적합한 경우 |
| --- | --- | --- | --- |
| **프롬프트 + few-shot** | 없음 | 제한적. SLM은 긴 지시를 잘 따르지 못함 | 빠른 실험, 과제 정의 초기 |
| **LoRA/QLoRA 미세 조정** | 낮음(수백~수천 예시, 단일 GPU 수 시간) | 크다. 형식 준수·도메인 용어·라벨 체계를 확실히 학습 | 평가 데이터가 있는 대부분의 과제 |
| **증류(distillation)** | 중간(교사 모델 호출 비용) | 크다. 대형 모델의 판단을 SLM이 모방 | 라벨은 없지만 대형 모델이 잘 푸는 과제 |
| **전체 미세 조정** | 높음 | LoRA 대비 소폭 우위 | 대규모 데이터, 도메인 사전학습 수준의 변화 필요 |

**증류 절차(가장 흔한 경로)**

1. 운영 로그나 샘플에서 입력 수천~수만 건을 모은다.
2. 대형 모델(교사)에게 과제를 수행시켜 출력을 라벨로 만든다. 필요하면 근거(rationale)도 함께 생성해 학습 신호를 풍부하게 한다.
3. 사람이 일부(수백 건)를 검수해 교사 출력의 품질을 확인하고 오류 패턴을 제거한다.
4. SLM을 LoRA로 미세 조정한다.
5. 검수된 평가 세트로 교사 대비 정확도를 측정한다. 90~95% 수준이면 비용 대비 충분한 경우가 많다.
6. 운영 중 SLM이 상위 계층으로 넘긴 사례를 모아 주기적으로 재학습한다.

이 절차는 대형 모델을 "라벨링 도구"로 쓰는 것이다. 교사 모델의 출력이 곧 학습 데이터이므로, 교사 프롬프트의 품질과 검수 단계가 SLM 품질의 상한을 정한다. 평가 방법은 [RAG·LLM 평가 데이터세트 구축과 오프라인 평가 하네스](./llm-evaluation-harness.md)를 따른다.

**주의점**

- 미세 조정한 SLM은 학습 분포 밖 입력에 취약하다. 입력 분포 변화를 감시하고(책 7.3.2), 신뢰도 낮은 입력은 상위 계층으로 넘기는 안전장치를 반드시 둔다.
- 과제 정의가 바뀌면(라벨 추가, 형식 변경) 재학습이 필요하다. 프롬프트 수정으로 끝나는 대형 모델보다 변경 비용이 크다. 과제가 안정된 뒤 SLM으로 옮기는 것이 순서다.

## 4. 서빙: 서버 측 SLM

SLM 서빙은 [LLM 추론 서빙 최적화](./llm-inference-serving.md)의 원칙을 따르되, 크기가 작아 선택지가 넓다.

- **GPU 공유**: 8B 모델은 FP8/INT8로 단일 GPU에 여러 인스턴스를 올릴 수 있다. vLLM의 다중 LoRA 서빙은 기본 모델 하나에 과제별 LoRA 어댑터 수십 개를 올려 요청마다 다른 어댑터를 적용한다. 과제마다 모델을 따로 띄우는 것보다 GPU 활용률이 훨씬 높다.
- **CPU 서빙**: 1~3B 모델은 llama.cpp(GGUF, INT4)로 CPU에서 초당 수십 토큰이 나온다. 분류·추출처럼 출력이 짧은 과제라면 GPU 없이 기존 CPU 서버 풀에서 서빙하는 것이 비용 면에서 유리할 수 있다.
- **배치 추론**: 실시간이 필요 없는 대량 처리(로그 분류, 상품 속성 추출)는 Spark·Ray 위에서 SLM을 배치로 돌린다. 웨어하우스·레이크하우스 플랫폼이 제공하는 배치 LLM 함수(`ai_query` 류)도 내부적으로 이 구조다.
- **스케일링 단위**: SLM은 콜드 스타트가 빨라(수 초~수십 초) 오토 스케일링과 서버리스 GPU에 잘 맞는다. 트래픽이 간헐적이면 상시 구동 대신 스케일-투-제로를 고려한다.

<br>

## 5. 온디바이스·엣지 추론

모델이 사용자 기기나 현장 장비에서 직접 실행되는 경우다. 서버 비용이 0이고 네트워크 지연이 없으며 데이터가 기기를 떠나지 않는다는 장점이 있지만, 하드웨어 제약과 배포·갱신의 어려움이 따른다.

**적합한 경우**

- 개인정보가 민감해 서버 전송을 피해야 하는 입력(메시지, 사진, 건강 데이터, 음성)
- 오프라인·저연결 환경(매장 단말, 물류 창고, 차량, 공장 설비)
- 초저지연 상호작용(입력 중 실시간 제안, 카메라 프레임 단위 인식)
- 사용자 수가 매우 많아 서버 추론 비용이 지배적인 소비자 앱

**실행 스택**

| 플랫폼 | 런타임 | 비고 |
| --- | --- | --- |
| iOS/macOS | Core ML, MLX, llama.cpp(Metal) | Apple Neural Engine 활용, Apple Foundation Models 프레임워크로 OS 내장 모델 호출 가능 |
| Android | LiteRT(TFLite 후속), MediaPipe LLM Inference, ONNX Runtime Mobile, llama.cpp | Gemini Nano 등 OS 내장 모델은 AICore API로 호출 |
| Windows | ONNX Runtime + DirectML, Windows ML | NPU 탑재 PC에서 Phi 계열 등 |
| 브라우저 | WebGPU 기반(Transformers.js, WebLLM) | 설치 없이 실행, 모델 다운로드 크기가 관건 |
| 엣지 서버·임베디드 | llama.cpp, ONNX Runtime, TensorRT(Jetson), OpenVINO | 현장 장비. [모델 변환과 경량화 실습](./model-conversion-onnx-tensorrt.md)의 변환 파이프라인이 그대로 적용 |

**설계 고려사항**

- **모델 크기 예산**: 스마트폰에서 현실적인 크기는 INT4 기준 1~4B(0.5~2.5GB)다. 다운로드·저장·메모리 모두를 고려한다. 앱 최초 실행 시 다운로드하거나 OS 내장 모델을 우선 활용해 배포 크기를 줄인다.
- **양자화 필수**: INT4(GGUF Q4, AWQ 등)가 기본이다. 정확도 저하를 평가 세트로 확인하고, 민감한 과제는 INT8을 검토한다.
- **하이브리드 구조**: 기기에서 1차 처리(분류, 개인정보 마스킹, 초안)를 하고 복잡한 요청만 서버로 보낸다. 2절의 계층화가 기기-서버 경계를 넘어 확장된 형태다. 기기에서 개인정보를 제거한 뒤 서버로 보내면 프라이버시와 품질을 함께 얻는다.
- **배포와 갱신**: 모델 파일은 앱 바이너리와 분리해 별도로 배포·버전 관리한다. 기기별 성능 편차가 크므로(구형 기기), 기기 사양에 따라 모델 크기를 다르게 내려주거나 서버 폴백을 둔다.
- **평가와 관측**: 기기에서의 품질은 서버처럼 로그를 다 모을 수 없다. 사용자 동의 하에 샘플링된 익명 지표(지연, 폴백 비율, 명시적 피드백)만 수집하고, 품질 평가는 출시 전 기기 매트릭스에서 오프라인으로 수행한다.
- **발열·배터리**: 지속적 추론은 배터리와 발열에 직접 영향을 준다. 추론 빈도 제한, 저전력 모드 감지, NPU 우선 사용을 설계에 넣는다.

## 6. 판단 체크리스트

SLM 도입을 검토할 때 순서대로 답한다.

1. 이 과제는 범위가 좁고 출력이 구조화되는가? 아니라면 대형 모델을 유지한다.
2. 평가 데이터(또는 교사 모델로 만들 수 있는 데이터)가 있는가? 없으면 먼저 만든다.
3. 월 호출량과 현재 API 비용은 얼마이며, SLM 서빙 고정비(GPU 또는 CPU 풀)와 비교해 손익분기를 넘는가?
4. 범용 SLM + 프롬프트로 목표 정확도의 80%에 도달하는가? 도달하면 미세 조정으로 나머지를 채울 가능성이 높다. 50% 미만이면 과제가 SLM 범위를 넘는다.
5. 신뢰도 낮은 입력을 상위 계층으로 넘기는 안전장치를 설계했는가?
6. 과제 정의가 앞으로 6개월 안정적인가? 자주 바뀌면 프롬프트 기반 대형 모델이 총비용에서 유리하다.
7. 온디바이스가 필요한가? 필요하다면 프라이버시·오프라인·지연 중 어느 이유이며, 그 이유가 배포·갱신 복잡도를 정당화하는가?

<br>
<br>

SLM의 부상은 "가장 큰 모델을 쓰자"에서 **"과제에 맞는 가장 작은 모델을 쓰자"** 로 기본값이 바뀌었음을 뜻한다. 이는 전통적 ML이 늘 해 온 일이다. 과제를 정의하고, 데이터를 모으고, 그 과제에 맞는 모델을 학습해 배포한다. 대형 API가 이 과정을 건너뛰게 해 주었지만, 규모가 커지면 결국 같은 규율로 돌아온다. 데이터·ML 팀의 기존 역량(평가 세트 구축, 미세 조정, 서빙 최적화, 드리프트 감시)이 LLM 시대에도 그대로 경쟁력이 되는 지점이 여기다.
