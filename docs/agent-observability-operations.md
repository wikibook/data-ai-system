# 에이전트 관측성과 운영(AgentOps)

책 7.3(모델 성능 모니터링)은 예측 모델의 드리프트와 성능 저하를, 9장(로그 설계와 운영)은 시스템 로그의 수집·분석을 다룬다. LLM 에이전트는 이 두 체계 어디에도 깔끔하게 들어가지 않는다. 요청 하나가 수십 번의 모델 호출과 도구 호출로 이루어지고, 같은 입력에도 매번 다른 경로를 밟으며, 실패가 오류 코드가 아닌 "그럴듯하지만 틀린 응답"으로 나타난다. 기존 APM은 HTTP 요청 하나를 추적하도록 만들어졌기 때문에, 에이전트 내부에서 무슨 일이 있었는지 보여주지 못한다. 이 문서는 에이전트를 운영 가능한 시스템으로 만드는 관측성(observability) 설계와 운영 절차를 정리한다.

[LLM 에이전트와 도구 호출 아키텍처](./llm-agent-architecture.md)가 에이전트를 만드는 방법을, [RAG·LLM 평가 데이터세트 구축과 오프라인 평가 하네스](./llm-evaluation-harness.md)가 배포 전 검증을 다룬다면, 이 문서는 배포 후를 다룬다.

<br>

## 1. 무엇이 다른가

| 관점 | 전통적 서비스 / 예측 모델 | LLM 에이전트 |
| --- | --- | --- |
| 요청 단위 | HTTP 요청 1건 = 처리 1회 | 요청 1건 = LLM 호출 N회 + 도구 호출 M회, N·M은 실행마다 다름 |
| 실패 형태 | 오류 코드, 예외, 타임아웃 | 대부분 200 OK. 틀린 답, 잘못된 도구 선택, 불필요한 반복, 조기 종료 |
| 비용 | 요청당 거의 일정 | 요청당 수십 배 차이. p99 비용이 평균의 20배인 경우도 흔함 |
| 재현 | 같은 입력 → 같은 출력 | 같은 입력 → 다른 경로. 재현에는 전체 컨텍스트 스냅샷 필요 |
| 변경 원인 | 코드 배포 | 코드, 프롬프트, 모델 버전, 도구 설명, 검색 색인, 모델 제공사의 무통보 갱신 |
| 품질 판단 | 지표로 자동 계산 | 사람 또는 LLM 판정이 필요 |

이 차이 때문에 에이전트 운영에는 세 가지가 추가로 필요하다. 요청 내부를 보여주는 **트레이싱**, 응답 품질을 지속적으로 재는 **온라인 평가**, 그리고 요청당 비용을 다루는 **비용 거버넌스**다.

<br>

## 2. 트레이싱: 요청 내부를 보이게 하기

### 2.1 트레이스 구조

에이전트 실행 하나를 하나의 트레이스(trace)로, 그 안의 각 LLM 호출·도구 호출·검색·가드레일 검사를 스팬(span)으로 기록한다.

```
Trace: 사용자 요청 "지난달 환불률이 왜 올랐는지 분석해줘"  (총 34.2s, 48,300 토큰, $0.41)
 ├─ span: 입력 가드레일 (0.1s)
 ├─ span: LLM 호출 #1 — 계획 수립 (2.1s, 3,200 in / 410 out, model=x-large, prompt=v12)
 ├─ span: 도구 run_query — 월별 환불률 (1.8s, 결과 24행)
 ├─ span: LLM 호출 #2 — 결과 해석·다음 행동 (3.4s, 5,100 in / 280 out)
 ├─ span: 도구 run_query — 카테고리별 환불률 (2.2s, 결과 200행, 잘림)
 ├─ span: LLM 호출 #3 (3.9s, 9,800 in / 350 out)
 ├─ span: 도구 run_query — 재시도, 집계 쿼리로 변경 (1.5s, 12행)
 ├─ span: LLM 호출 #4 — 최종 응답 (6.2s, 11,400 in / 1,200 out)
 ├─ span: 출력 가드레일 (0.2s)
 └─ span: 온라인 판정 (비동기, faithfulness=pass)
```

이 구조가 있으면 "왜 34초가 걸렸는가"(LLM 호출 4회 중 마지막이 6초), "왜 비용이 높았는가"(잘린 200행 결과가 다음 호출 입력을 키움), "어디서 방향이 틀어졌는가"를 스팬 단위로 볼 수 있다.

### 2.2 스팬에 기록할 것

| 스팬 종류 | 필수 속성 | 비고 |
| --- | --- | --- |
| **LLM 호출** | 모델 이름·버전, 프롬프트 템플릿 버전, 입력·출력 토큰, 지연(TTFT 포함), 종료 이유, temperature, 캐시 적중 토큰 | 프롬프트·응답 본문은 별도 저장소에 두고 참조 ID를 남긴다(용량·개인정보) |
| **도구 호출** | 도구 이름, 인자 요약, 결과 크기(바이트·토큰), 잘림 여부, 성공/실패, 지연 | 인자·결과 원문은 마스킹 후 저장 |
| **검색** | 질의, 반환 문서 ID와 점수, 후보 수, 인덱스 버전 | RAG 디버깅의 핵심 |
| **가드레일** | 종류, 판정, 점수, 차단 여부 | 오탐 분석용 |
| **트레이스 공통** | 사용자·세션 ID(해시), 에이전트 버전, 총 토큰·비용·지연, 최종 상태(완료/예산 초과/오류/사용자 중단) | 대시보드 집계 기준 |

**표준: OpenTelemetry GenAI 시맨틱 컨벤션**

LLM 호출 스팬의 속성 이름(`gen_ai.request.model`, `gen_ai.usage.input_tokens`, `gen_ai.operation.name` 등)은 OpenTelemetry의 GenAI 시맨틱 컨벤션으로 표준화되고 있다. 이 컨벤션을 따르면 기존 APM(Datadog, Grafana Tempo, Jaeger)과 LLM 전용 도구(Langfuse, LangSmith, Arize Phoenix) 어느 쪽으로도 같은 데이터를 보낼 수 있다. 자체 필드를 만들기 전에 컨벤션에 있는지 먼저 확인한다.

### 2.3 컨텍스트 전파

에이전트가 MCP 서버나 서브 에이전트를 호출할 때 트레이스 ID를 함께 전달해야 전체 경로가 하나로 이어진다. HTTP 헤더(W3C Trace Context)로 전파하는 것이 표준이며, [MCP 서버 설계와 운영 실무](./mcp-server-design.md)의 서버 측 로깅과 여기서 만난다.

## 3. 지표: 무엇을 대시보드에 올리는가

### 3.1 경로(trajectory) 지표

응답 품질 이전에, 에이전트가 **어떻게 일했는가**를 재는 지표다. 품질 저하보다 먼저 움직이는 선행 지표 역할을 한다.

| 지표 | 계산 | 이상 신호 |
| --- | --- | --- |
| 요청당 LLM 호출 수(p50/p95) | 트레이스 내 LLM 스팬 수 | p95 급증 → 루프, 도구 오류 반복 |
| 요청당 도구 호출 수, 도구별 비율 | 도구 스팬 집계 | 특정 도구 비율 급변 → 도구 설명·프롬프트 변경 영향 |
| 도구 오류율, 재시도율 | 실패 스팬 / 전체 | 상승 → 도구 계약 변경, 다운스트림 장애 |
| 동일 호출 반복률 | 같은 도구·같은 인자 연속 호출 | 상승 → 루프 |
| 예산 초과 종료 비율 | 최종 상태 = 예산 초과 | 상승 → 과제 난이도 증가 또는 회귀 |
| 사람 승인 요청·거부 비율 | 승인 스팬 집계 | 거부 급증 → 에이전트가 이상한 행동을 제안 |
| 도구 결과 잘림 비율 | 잘림 플래그 | 높음 → 도구 결과 설계 재검토 |

### 3.2 품질 지표(온라인 평가)

- **샘플링 판정**: 운영 트래픽의 일부(1~5%)에 오프라인 하네스와 동일한 LLM 판정(faithfulness, 과제 완료 여부, 지시 준수)을 비동기로 적용한다. 전량 판정은 비용이 크므로, 고위험 요청 유형이나 이상 신호가 있는 트레이스는 샘플링 비율을 높인다.
- **사용자 신호**: 명시적 피드백(좋아요/싫어요), 암묵적 신호(재질문, 응답 수정 요청, 중단, 같은 질문 재시도, 후속 행동 완료 여부). 명시적 피드백은 응답률이 낮아 편향이 있으므로 암묵적 신호를 함께 본다.
- **거부·에스컬레이션 비율**: 에이전트가 "할 수 없다"고 답하거나 사람에게 넘긴 비율. 너무 낮으면 과신, 갑자기 높아지면 도구·권한 문제다.

### 3.3 비용·지연 지표

- 요청당 비용 분포(p50/p95/p99)와 **일별 총비용**. 평균만 보면 소수의 폭주 요청이 비용의 절반을 차지하는 것을 놓친다.
- 요청 유형·사용자 그룹·프롬프트 버전별 비용. 어떤 변경이 비용을 올렸는지 귀속시킬 수 있어야 한다.
- 캐시 적중 토큰 비율. 프리픽스 캐싱이 깨졌는지 감시한다.
- E2E 지연 p95와 스팬별 기여도. 어느 단계가 지연을 지배하는지 본다.

**대시보드 구성 예**

```
[1행] 요청 수 / 완료율 / 예산 초과율 / 오류율          ← 건강 상태
[2행] 요청당 비용 p50·p95·p99 / 일 총비용 / 캐시 적중률  ← 비용
[3행] LLM 호출 수 p95 / 도구 오류율 / 반복 호출률       ← 경로 이상
[4행] 온라인 판정 통과율 / 부정 피드백률 / 거부율        ← 품질
[5행] 프롬프트·모델 버전별 위 지표 비교                  ← 변경 영향
```

## 4. 알림과 대응

**알림 규칙 예**

| 조건 | 심각도 | 1차 대응 |
| --- | --- | --- |
| 도구 오류율 > 10% (5분) | 높음 | 해당 도구의 다운스트림 상태 확인, 도구 계약 변경 여부 확인 |
| 요청당 LLM 호출 p95 > 기준 2배 | 높음 | 최근 프롬프트·도구 설명 변경 롤백 검토, 루프 트레이스 샘플 확인 |
| 일 비용이 예산의 80% 도달 | 중간 | 요청 유형별 비용 귀속, 필요 시 요청당 예산 상한 하향 |
| 온라인 판정 통과율 5%p 하락 (1시간) | 높음 | 모델 제공사 변경 공지 확인, 오프라인 하네스 재실행 |
| 캐시 적중률 급락 | 중간 | 시스템 프롬프트 앞부분에 가변 값 유입 여부 확인 |
| 가드레일 차단률 급증 | 중간 | 인젠션 시도 여부 확인, 오탐 여부 확인 |
| 사람 승인 거부율 > 30% | 높음 | 에이전트 제안 내용 샘플 검토, 쓰기 도구 임시 비활성화 |

**변경 관리**

에이전트의 행동을 바꾸는 변경은 코드 외에도 많다. 다음 모두를 **배포**로 취급해 버전을 기록하고 트레이스에 태깅한다.

- 프롬프트 템플릿(시스템 프롬프트, 판정 프롬프트)
- 모델 이름·버전(제공사의 자동 갱신은 고정 버전 지정으로 막는다)
- 도구 정의·설명(MCP 서버 배포 포함)
- 검색 색인 버전, 임베딩 모델
- 가드레일 규칙·임곗값
- 에이전트 오케스트레이션 코드

배포는 점진적으로(카나리 5% → 25% → 100%) 하고, 각 단계에서 위 지표를 이전 버전과 비교한다. 책 7.2.2의 배포 시나리오가 그대로 적용되며, 차이는 비교 대상이 정확도가 아니라 경로·비용·판정 지표라는 점이다.

**롤백 기준**

어떤 지표가 얼마나 나빠지면 자동 롤백할지 배포 전에 정한다. "온라인 판정 통과율 3%p 하락 또는 요청당 비용 30% 상승"처럼 수치로 둔다. 판단을 배포 후에 하면 늦다.

## 5. 사고 조사(디버깅) 절차

품질 사고는 대개 "고객이 이상한 답을 받았다"는 제보로 시작한다. 재현이 어렵기 때문에 절차가 필요하다.

1. **트레이스 확보**: 세션 ID나 시간으로 트레이스를 찾는다. 이것이 가능하려면 사용자 화면에 요청 ID가 노출되거나, 피드백 버튼이 트레이스 ID를 함께 보내야 한다.
2. **경로 확인**: 어느 스팬에서 갈라졌는지 본다. 검색이 잘못된 문서를 반환했는가(검색 스팬의 문서 ID), 도구가 잘린 결과를 줬는가, 모델이 도구 결과를 오해석했는가(다음 LLM 스팬의 출력), 프롬프트 버전이 예상과 다른가.
3. **재현**: 트레이스에 기록된 컨텍스트 스냅샷(프롬프트 버전, 검색 문서, 도구 결과)으로 해당 LLM 호출만 다시 실행한다. 전체 에이전트를 다시 돌리면 다른 경로를 밟는다. 이를 위해 트레이스가 각 호출의 **전체 입력**을 재구성할 수 있어야 한다.
4. **분류**: 원인을 검색 / 도구 / 프롬프트 / 모델 / 데이터 중 하나로 태깅한다. 분류 통계가 다음 분기 개선 우선순위가 된다.
5. **평가 세트 추가**: 재현된 사례를 오프라인 하네스에 추가해 같은 실패가 재발하지 않게 한다. 이 환류가 없으면 같은 사고를 반복한다.

<br>

## 6. 개인정보와 보존

트레이스에는 사용자 입력·검색 문서·도구 결과가 담기므로 개인정보가 섞인다.

- 저장 전 PII 마스킹(전화번호, 이메일, 주민등록번호, 카드번호 패턴)을 기본 적용한다. 판정·디버깅에 원문이 필요하면 접근 통제된 별도 저장소에 짧은 보존 기간으로 둔다.
- 보존 기간을 정한다. 지표 집계는 장기, 본문은 단기(예: 30일)가 일반적이다.
- 사용자 삭제 요청 시 트레이스에서 해당 사용자 데이터를 찾아 지울 수 있어야 한다. 사용자 ID를 해시로 저장하되 매핑을 별도로 관리한다.
- 트레이스 접근 자체를 감사 로그로 남긴다. 책 13.2.4의 보안 모니터링·감사 원칙이 적용된다.

## 7. 도구 선택

| 구분 | 예 | 특징 |
| --- | --- | --- |
| LLM 전용 관측 플랫폼 | Langfuse(오픈소스), LangSmith, Arize Phoenix(오픈소스), Braintrust, W&B Weave | 트레이스 UI가 LLM 호출에 최적화, 프롬프트 관리·평가 데이터세트·온라인 판정 내장 |
| 범용 APM + GenAI 컨벤션 | Datadog LLM Observability, Grafana Tempo + OTel, Honeycomb | 기존 인프라 모니터링과 한 화면, 팀이 이미 쓰는 도구 재활용 |
| 자체 구축 | OpenTelemetry SDK → 컬렉터 → 데이터 웨어하우스 | 완전한 통제, 비용 분석을 SQL로. UI는 직접 만들어야 함 |

일반적인 선택은 **OpenTelemetry로 계측하고 백엔드는 나중에 고르는** 것이다. 계측을 특정 벤더 SDK로 하면 옮기기 어렵다. 초기에는 오픈소스 LLM 관측 도구로 시작해 트레이스 UI를 얻고, 지표는 기존 모니터링 스택(Prometheus·Grafana, 책 부록 A.6)으로 보내는 조합이 무난하다.

에이전트 운영의 요체는 **"응답이 왔다"와 "일이 제대로 되었다"를 구분해서 재는 것**이다. 오류율 0%, 지연 정상인 에이전트가 조용히 틀린 답을 내고 있을 수 있다. 트레이스로 내부를 보이게 하고, 경로 지표로 이상을 먼저 잡고, 샘플 판정으로 품질을 지속적으로 확인하며, 모든 실패를 평가 세트로 돌려보내는 순환이 갖춰졌을 때 에이전트는 데모가 아닌 서비스가 된다.
