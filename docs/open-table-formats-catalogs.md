# 오픈 테이블 포맷과 카탈로그 표준

책 6.2.4(클라우드 기반 데이터 웨어하우스)와 부록 B.5(데이터 레이크하우스 아키텍처)는 레이크하우스를 "레이크의 저렴한 저장과 웨어하우스의 관리 기능을 결합한 구조"로 소개했다. 2026년 현재 이 구조의 실체는 꽤 구체적으로 굳어졌다. 저장은 객체 스토리지의 Parquet 파일, 테이블 관리는 **Apache Iceberg**(또는 Delta Lake), 테이블의 위치·스키마·권한을 관리하는 것은 **REST 카탈로그**, 그리고 그 위에서 Spark·Trino·DuckDB·Snowflake·BigQuery·Databricks 등 **여러 엔진이 같은 테이블을 읽고 쓴다**. 이 문서는 "엔진 중립·카탈로그 중립" 아키텍처가 무엇을 바꾸는지, 그리고 그 위에서 데이터·ML 팀이 결정해야 할 것들을 정리한다.

<br>

## 1. 왜 테이블 포맷이 중요해졌는가

객체 스토리지에 Parquet 파일을 쌓는 "1세대 데이터 레이크"는 다음 문제를 안고 있었다. 파일 목록이 곧 테이블이라 디렉터리 스캔이 느리고, 쓰는 도중 읽으면 불완전한 결과가 나오며(원자성 부재), 스키마 변경은 파일을 다시 쓰는 일이었고, 삭제·갱신은 파티션 전체를 재작성해야 했다.

오픈 테이블 포맷은 파일 위에 **메타데이터 계층**을 두어 이를 해결한다.

```
[카탈로그]  ─ 테이블 이름 → 현재 메타데이터 파일 포인터 (원자적 교체)
    │
    ▼
[메타데이터 파일]  ─ 스키마(버전별), 파티션 스펙, 스냅샷 목록
    │
    ▼
[매니페스트 목록 → 매니페스트]  ─ 스냅샷에 속한 데이터 파일 목록 + 컬럼 통계(min/max, null 수)
    │
    ▼
[데이터 파일 (Parquet / ORC)]  ─ 실제 행 데이터
```

이 구조가 주는 것은 다음과 같다.

| 기능 | 의미 | 데이터·ML 팀에 주는 효과 |
| --- | --- | --- |
| **ACID 트랜잭션** | 스냅샷 단위 원자적 커밋, 동시 쓰기 충돌 감지 | 배치 적재 중 읽어도 일관된 결과, 스트리밍·배치 동시 쓰기 |
| **스키마 진화** | 컬럼 추가·삭제·이름 변경·타입 확장을 메타데이터만으로 | 파일 재작성 없는 스키마 변경([데이터 계약과 스키마 진화](./data-contracts-schema-evolution.md)) |
| **타임 트래블** | 과거 스냅샷 조회 | 학습 데이터 재현, 파이프라인 오류 시 롤백 |
| **숨은 파티셔닝** | 파티션 변환(`day(ts)`)을 테이블이 관리, 쿼리는 원 컬럼으로 필터 | 사용자가 파티션 컬럼을 몰라도 프루닝, 파티션 스펙 변경 가능 |
| **행 수준 갱신·삭제** | MERGE, DELETE 지원 | CDC 반영, 개인정보 삭제 요청 처리 |
| **통계 기반 프루닝** | 매니페스트의 컬럼 min/max로 파일 스킵 | 디렉터리 스캔 없이 빠른 계획, 비용 절감 |

## 2. 포맷 비교와 현재의 수렴

| 포맷 | 출신 | 현재 위치 |
| --- | --- | --- |
| **Apache Iceberg** | Netflix → Apache | 엔진 중립 표준으로 수렴. Snowflake·BigQuery·Databricks·AWS·Trino·DuckDB 등 대부분이 읽기·쓰기 지원. REST 카탈로그 사양이 카탈로그 상호운용의 기준 |
| **Delta Lake** | Databricks → Linux Foundation | Databricks 생태계의 기본. UniForm으로 Iceberg 메타데이터를 함께 생성해 Iceberg 리더가 읽을 수 있음 |
| **Apache Hudi** | Uber → Apache | 증분 처리·CDC 업서트에 강점. 채택 범위는 앞의 둘보다 좁음 |
| **Apache Paimon** | Flink 커뮤니티 | 스트리밍 우선 설계. Flink 중심 조직에서 채택 |

실무적 결론은 명확하다. **새로 시작하면 Iceberg**, Databricks 중심이면 Delta + UniForm으로 Iceberg 호환을 확보한다. Databricks가 Iceberg의 주요 기업(Tabular)을 인수한 뒤 두 포맷은 상호운용 방향으로 수렴하고 있어, 포맷 자체보다 다음 절의 카탈로그 선택이 더 중요한 결정이 되었다.

<br>

## 3. 카탈로그: 새로운 통제 지점

테이블 포맷이 "파일을 테이블로 보이게" 한다면, 카탈로그는 "어떤 테이블이 어디에 있고 누가 접근할 수 있는가"를 관리한다. 여러 엔진이 같은 테이블을 쓰는 구조에서 카탈로그는 **권한·계보·감사가 모이는 단일 지점**이 되었고, 그래서 플랫폼 벤더들이 가장 치열하게 경쟁하는 자리다.

### 3.1 Iceberg REST Catalog 사양

Iceberg는 카탈로그와의 통신을 REST API 사양으로 표준화했다. 엔진은 이 API만 구현하면 어떤 카탈로그든 쓸 수 있고, 카탈로그는 이 API만 제공하면 어떤 엔진이든 받을 수 있다. 사양에는 자격 증명 위임(vended credentials)이 포함되어, 엔진이 스토리지 자격 증명을 직접 갖지 않고 카탈로그가 테이블별로 발급한 임시 자격 증명을 쓴다. 이것이 **카탈로그가 권한의 단일 지점이 될 수 있는 기술적 근거**다.

### 3.2 카탈로그 선택지

| 카탈로그 | 성격 | 특징 |
| --- | --- | --- |
| **Apache Polaris** | 오픈소스(Snowflake 기여) | Iceberg REST 사양의 참조 구현에 가까움. 벤더 중립을 원하는 조직의 자체 운영 선택지 |
| **Unity Catalog** | Databricks(오픈소스 버전 존재) | Delta·Iceberg 모두 관리, Iceberg REST 엔드포인트 제공. 계보·권한·시맨틱(Metric Views)·ML 자산(모델, 피처)까지 한 카탈로그에서 관리 |
| **AWS Glue Data Catalog / S3 Tables** | AWS 관리형 | AWS 생태계 통합, Lake Formation 권한. S3 Tables는 Iceberg 테이블 유지관리(컴팩션)를 스토리지가 자동 수행 |
| **Snowflake Open Catalog** | Polaris 관리형 | Snowflake 외부 엔진에도 Iceberg 테이블 개방 |
| **BigQuery / BigLake Metastore** | GCP 관리형 | BigQuery와 Spark 등 외부 엔진의 Iceberg 테이블 공유 |
| **Nessie, Lakekeeper, Gravitino** | 오픈소스 | Nessie는 Git 유사 브랜치·태그, Lakekeeper는 경량 Rust 구현, Gravitino는 다중 소스 메타데이터 통합 |

### 3.3 선택 기준

- **권한 모델의 위치**: 권한을 카탈로그 한곳에서 관리하고 모든 엔진에 강제할 수 있는가. 엔진마다 권한을 따로 관리하면 카탈로그 중립의 의미가 없다. 자격 증명 위임 지원 여부를 확인한다.
- **자산 범위**: 테이블만 관리하는가, 모델·피처·함수·비정형 파일(볼륨)까지 관리하는가. ML 팀은 학습 데이터(테이블)와 모델·피처(비테이블)의 계보를 잇고 싶어 하므로 범위가 넓은 쪽이 유리하다.
- **종속성**: 관리형 카탈로그는 운영 부담이 없지만, 카탈로그가 곧 플랫폼 종속의 새 지점이 된다. "테이블은 열려 있는데 카탈로그는 닫혀 있다"는 상황을 의식적으로 평가한다. 오픈소스 카탈로그로의 이전 경로가 있는지 본다.
- **운영 기능**: 컴팩션·스냅샷 만료·고아 파일 정리 같은 테이블 유지관리를 카탈로그(또는 스토리지)가 자동으로 해 주는지, 직접 스케줄링해야 하는지.

<br>

## 4. 다중 엔진 아키텍처

카탈로그 중립이 가능해지면서 "작업에 맞는 엔진을 고르는" 구조가 현실이 되었다.

```
[카탈로그] ─ 스키마·권한·계보의 단일 지점
   │
   ├─▶ Spark        ─ 대규모 배치, 피처 생성
   ├─▶ Flink        ─ 스트리밍 적재, CDC 반영
   ├─▶ Trino        ─ 대화형 SQL, BI·데이터 에이전트
   ├─▶ DuckDB       ─ 로컬·소규모 개발·테스트
   ├─▶ Snowflake / BigQuery ─ BI, 재무 보고
   └─▶ ML 학습 프레임워크(PyTorch, Ray 등) ─ 학습 데이터 직접 읽기
   │
   ▼
[객체 스토리지] ─ Iceberg 테이블 (Parquet 데이터 파일 + 메타데이터)
```

**데이터·ML 팀에게 열리는 것**

- **학습 데이터를 복사하지 않는다**: 웨어하우스에서 내보내 S3에 올리는 대신, 학습 프레임워크가 Iceberg 테이블을 직접 읽는다(PyIceberg, Ray Data, Daft 등). 스냅샷 ID를 학습 메타데이터에 기록하면 재현성이 확보된다.
- **엔진별 비용 최적화**: 대화형 탐색은 DuckDB로 노트북에서 무료로, 대규모 피처 생성은 Spark로, BI는 웨어하우스로. 같은 테이블이므로 결과가 일치한다.
- **스트리밍과 배치의 통합**: Flink가 Iceberg 테이블에 스트리밍으로 쓰고, 같은 테이블을 Spark 배치가 읽는다. 책 8.4.3의 하이브리드 아키텍처가 두 저장소가 아닌 하나의 테이블로 구현된다.
- **브랜치와 태그**: Iceberg의 브랜치·태그(Nessie는 카탈로그 수준에서)로 "학습용 스냅샷 v3", "검증 전 적재 브랜치"를 만든다. 데이터에 Git 유사 워크플로가 생긴다.

**주의점**

- 엔진별 Iceberg 기능 지원 범위가 다르다(행 수준 삭제 방식, 파티션 변환, v3 스펙 기능 등). "읽기는 어디서나, 쓰기는 한두 엔진에서"로 시작하는 것이 안전하다.
- 동시 쓰기는 낙관적 동시성 제어로 충돌을 감지하지만, 같은 파티션에 여러 엔진이 동시에 쓰면 재시도가 잦아진다. 쓰기 소유자를 테이블별로 정한다.

<br>

## 5. 운영: 테이블 유지관리

Iceberg 테이블은 방치하면 느려진다. 작은 파일이 쌓이고, 스냅샷이 누적되어 메타데이터가 커지며, 삭제된 데이터의 파일이 남는다. 다음 작업을 정기적으로 실행해야 하며, 관리형 카탈로그·스토리지가 자동화해 주는지가 운영 부담을 결정한다.

| 작업 | 목적 | 주기(예) |
| --- | --- | --- |
| **컴팩션(rewrite data files)** | 작은 파일을 목표 크기(128~512MB)로 병합, 정렬 적용 | 스트리밍 테이블은 시간 단위, 배치 테이블은 일 단위 |
| **매니페스트 재작성** | 매니페스트 파일 정리로 계획 시간 단축 | 컴팩션과 함께 |
| **스냅샷 만료(expire snapshots)** | 보존 기간 지난 스냅샷 제거, 참조 없는 파일 삭제 | 일 단위. 보존 기간은 타임 트래블 요구(재현성)와 저장 비용의 절충 |
| **고아 파일 정리(remove orphan files)** | 실패한 쓰기가 남긴 미참조 파일 삭제 | 주 단위. 진행 중인 쓰기 파일을 지우지 않도록 충분한 유예 |
| **삭제 파일 병합** | 행 수준 삭제(delete files) 누적 시 읽기 성능 저하 방지 | MERGE·DELETE 빈도에 따라 |

**ML 관점의 보존 정책**: 학습에 사용한 스냅샷은 만료되면 재현이 불가능해진다. 학습 파이프라인이 사용한 스냅샷에 태그를 붙여 만료에서 제외하거나, 학습 데이터 스냅샷을 별도 테이블로 물리 복제하는 정책을 정한다. 책 15.2.2의 모델 체크포인트 관리와 짝을 이루는 "데이터 체크포인트" 정책이다.

<br>

## 6. 이전 전략

기존 레이크(원시 Parquet, Hive 테이블)나 웨어하우스 전용 테이블에서 Iceberg로 옮기는 일반적인 순서다.

1. **새 테이블부터**: 신규 파이프라인의 출력은 모두 Iceberg로 만든다. 기존 테이블은 건드리지 않는다.
2. **읽기 통합**: 카탈로그를 세우고 기존 Hive 테이블도 등록해 한 카탈로그에서 보이게 한다. 엔진들의 카탈로그 연결을 통일한다.
3. **인플레이스 이전**: Hive 테이블은 데이터 파일을 재작성하지 않고 메타데이터만 생성해 Iceberg로 전환할 수 있다(`migrate`, `snapshot` 프로시저). 큰 테이블에 유리하다.
4. **소비자 전환**: 확장-축소 패턴으로 소비자를 새 테이블로 옮기고 구 테이블을 폐기한다.
5. **웨어하우스 네이티브 테이블**: 여러 엔진이 읽어야 하는 것부터 Iceberg 외부 테이블로 전환한다. 웨어하우스 안에서만 쓰는 테이블은 네이티브 포맷이 성능·기능 면에서 나을 수 있으므로 억지로 옮기지 않는다.

<br>
<br>

레이크하우스 아키텍처의 핵심 변화는 **저장·테이블 포맷이 열리면서 통제 지점이 카탈로그로 이동했다는 것**이다. 엔진은 갈아탈 수 있게 되었고, 그만큼 카탈로그 선택이 장기적 종속성을 결정한다. 데이터·ML 팀은 "어떤 엔진을 쓰는가"보다 "테이블·모델·피처의 스키마와 권한과 계보를 어디서 한 번에 관리하는가"를 먼저 결정해야 한다. 그 결정이 서 있으면, 학습 데이터 복사·엔진별 결과 불일치·재현 불가 같은 오랜 문제들이 구조적으로 해결된다.
