# LLM 에이전트와 도구 호출 아키텍처

책에서 "에이전트"는 주로 4.4(강화 학습)의 환경과 상호작용하는 학습 주체를 의미한다. 이 문서에서 다루는 LLM 에이전트는 그와 다르다. 대규모 언어 모델이 사용자 목표를 받아 **어떤 도구를 어떤 순서로 호출할지 스스로 결정하고, 결과를 보고 다음 행동을 고치는 반복 구조**를 가리킨다. 책 12.3.4(모델 컨텍스트 프로토콜, MCP)가 도구를 모델에 연결하는 표준을 소개했다면, 이 문서는 그 위에서 에이전트를 설계할 때의 구조·상태 관리·실패 복구·비용 통제를 정리한다.

<br>

## 1. 단순 호출에서 에이전트까지

LLM 활용 구조는 자율성의 정도에 따라 단계적으로 나눌 수 있다. 위로 갈수록 유연하지만 예측 가능성과 비용 통제가 어려워진다.

| 단계 | 구조 | 제어 주체 | 예시 |
| --- | --- | --- | --- |
| **단일 호출** | 프롬프트 → 응답 | 코드 | 분류, 요약, 추출 |
| **체인(chain)** | 고정된 순서의 여러 호출 | 코드 | 검색 → 생성(RAG), 초안 → 검토 → 수정 |
| **라우터(router)** | 모델이 분기 하나를 선택, 이후는 고정 | 코드 + 모델(1회 판단) | 의도 분류 후 전용 파이프라인 실행 |
| **도구 호출 루프** | 모델이 도구 선택·호출을 반복, 종료도 모델이 결정 | 모델 | 질문에 답하기 위해 DB 조회·계산·검색을 필요한 만큼 수행 |
| **다중 에이전트** | 역할이 다른 에이전트가 협업, 오케스트레이터가 조정 | 모델(여러 계층) | 기획-실행-검토 분업, 병렬 조사 후 종합 |

설계의 첫 원칙은 **필요한 최소한의 자율성만 부여하는 것**이다. 작업 흐름이 미리 정해질 수 있다면 체인으로 구현하는 것이 에이전트보다 빠르고 싸고 디버깅이 쉽다. 에이전트가 정당화되는 경우는 필요한 단계 수나 순서를 사전에 알 수 없고, 중간 결과에 따라 경로가 달라지는 과제다.

<br>

## 2. 도구 호출 루프의 기본 구조

```
사용자 목표
   │
   ▼
[LLM 호출]
   입력: 시스템 프롬프트 + 대화 이력 + 도구 스키마 + 이전 도구 결과
   출력: (a) 최종 응답 → 종료
         (b) 도구 호출 요청 [도구 이름, 인자]
   │ (b)
   ▼
[도구 호출 게이트] ─ 스키마 검증 → 권한 확인 → (위험 행동이면) 사용자 승인
   │
   ▼
[도구 실행] ─ 결과를 <tool_result>로 감싸 대화 이력에 추가
   │
   ▼
[종료 조건 검사] ─ 최대 반복 횟수·토큰 예산·시간 초과 여부
   │
   └─▶ 다시 [LLM 호출]로
```

**도구 정의**

도구는 이름, 설명, 입력 스키마(JSON Schema)로 모델에 노출된다. 모델은 설명을 읽고 도구를 선택하므로, 설명의 품질이 곧 에이전트의 정확도를 결정한다.

```json
{
  "name": "search_orders",
  "description": "고객 ID 또는 주문번호로 주문 내역을 조회한다. 배송 상태 문의, 환불 가능 여부 확인에 사용한다. 최근 90일 이내 주문만 반환한다.",
  "input_schema": {
    "type": "object",
    "properties": {
      "customer_id": {"type": "string", "description": "고객 고유 ID. 주문번호가 있으면 생략 가능"},
      "order_id":    {"type": "string", "description": "주문번호(예: ORD-20250612-001234)"},
      "status":      {"type": "string", "enum": ["all", "shipping", "delivered", "cancelled"], "default": "all"}
    }
  }
}
```

설명 작성 시 유의점은 다음과 같다.

- **언제 쓰는지와 언제 쓰지 않는지**를 함께 적는다. "환불 처리에는 `request_refund`를 사용한다"처럼 인접 도구와의 경계를 명시하면 오선택이 줄어든다.
- **반환 범위와 제약**(기간, 최대 건수, 권한)을 적어 모델이 결과 부재를 올바르게 해석하게 한다.
- 도구 수는 **10~20개 이내**가 안정적이다. 그 이상이면 관련 도구만 동적으로 노출하거나(도구 검색), 도메인별 하위 에이전트로 나눈다.
- 결과는 **모델이 읽기 좋은 형태**로 가공해 반환한다. 원시 JSON 수천 줄보다 요약된 표나 핵심 필드만 담은 결과가 정확도와 비용 모두에 유리하다. 긴 결과는 잘라내고 "전체 N건 중 상위 10건"임을 명시한다.

**MCP와의 관계**

MCP는 위 도구 정의·호출·결과 반환을 표준 프로토콜로 규격화해, 도구 제공자(서버)와 에이전트(클라이언트)를 분리한다. 사내 시스템을 MCP 서버로 감싸 두면 여러 에이전트·여러 모델에서 재사용할 수 있다. 다만 MCP는 연결 표준일 뿐, 어떤 도구를 노출하고 권한을 어떻게 통제할지는 여전히 에이전트 설계자의 책임이다. 서버 쪽 설계는 [MCP 서버 설계와 운영 실무](./mcp-server-design.md)에서 다룬다.

## 3. 설계 패턴

### 3.1 계획-실행 분리(Plan-and-Execute)

매 스텝마다 "다음 한 행동"만 결정하는 ReAct 방식은 단순하지만, 긴 과제에서 방향을 잃거나 같은 도구를 반복 호출하기 쉽다. 계획-실행 분리는 먼저 전체 계획(하위 작업 목록)을 세우고, 각 하위 작업을 실행한 뒤 계획을 갱신한다.

- 계획 단계에는 추론 능력이 높은 대형 모델을, 실행 단계에는 저렴한 모델을 쓸 수 있어 비용을 줄인다.
- 계획을 사용자에게 먼저 보여 승인받는 흐름을 자연스럽게 넣을 수 있다.
- 계획이 틀렸을 때 재계획 비용이 발생하므로, 실행 중 "계획 수정이 필요한가"를 판단하는 단계를 둔다.

### 3.2 오케스트레이터-워커(다중 에이전트)

하나의 오케스트레이터가 과제를 분해해 전문화된 워커 에이전트에게 위임하고 결과를 종합한다.

- **적합한 경우**: 독립적으로 병렬 수행할 수 있는 하위 작업(여러 출처 조사, 여러 파일 수정), 서로 다른 도구 집합이 필요한 작업, 컨텍스트가 너무 커서 하나의 대화에 담기지 않는 작업.
- **비용**: 에이전트 간 통신마다 컨텍스트가 복제되므로 토큰 사용량이 단일 에이전트의 수 배가 된다. 병렬화로 얻는 시간 이득이 비용을 정당화하는지 확인한다.
- **인터페이스 설계**: 워커에게 넘기는 지시는 "목표·제약·기대 출력 형식"을 명시한 자족적(self-contained) 프롬프트여야 한다. 워커는 오케스트레이터의 대화 이력을 보지 못한다.

### 3.3 검토자(Reflection / Critic)

생성 결과를 별도 호출로 검토하고 문제가 있으면 수정하게 한다. 코드 생성 후 테스트 실행, 문서 작성 후 체크리스트 검토가 대표적이다. 검토자는 실행자와 다른 프롬프트(가능하면 다른 모델)를 써야 같은 실수를 반복하지 않는다. 반복 횟수 상한(보통 2~3회)을 두지 않으면 비용이 발산한다.

### 3.4 사람 개입(Human-in-the-loop)

에이전트가 특정 지점에서 멈추고 사용자 입력을 기다리는 구조다. 위험한 행동 승인, 모호한 요구사항 확인, 계획 검토에 사용한다. 이를 위해 에이전트 상태를 **직렬화하고 나중에 복원**할 수 있어야 하며, 이것이 다음 절의 상태 관리와 직결된다.

## 4. 상태와 메모리 관리

에이전트의 상태는 대화 이력(메시지 목록)과 작업 상태(계획, 중간 결과, 변수)로 나뉜다.

**컨텍스트 창 관리**

- 도구 결과가 이력에 누적되면 컨텍스트가 빠르게 소진된다. 오래된 도구 결과는 요약으로 대체하거나 참조 ID만 남기고 본문은 외부 저장소에 둔다.
- 긴 작업은 **체크포인트**를 만든다. 지금까지의 진행 상황·결정 사항·남은 작업을 구조화된 요약으로 작성하고, 새 컨텍스트에서 그 요약으로 재시작한다.
- 시스템 프롬프트·도구 스키마처럼 매 호출에 반복되는 부분은 프리픽스 캐싱의 혜택을 받도록 앞쪽에 고정 배치한다. [LLM 추론 서빙 최적화](./llm-inference-serving.md) 2절을 참고한다. 컨텍스트 예산 배분과 압축·격리 기법 전반은 [컨텍스트 엔지니어링](./context-engineering.md)에서 다룬다.

**외부 메모리**

- **작업 메모리**: 현재 과제의 계획·중간 결과를 키-값 저장소나 파일에 두고 도구로 읽고 쓴다. 컨텍스트 창 한계를 넘는 작업의 기본 수단이다.
- **장기 메모리**: 사용자 선호, 과거 결정, 도메인 지식을 벡터 저장소에 두고 필요할 때 검색한다. 구조적으로는 RAG와 같으므로 [RAG 품질 저하 요인과 대응 전략](./rag-quality-risks.md)의 고려사항이 그대로 적용된다.
- **상태 직렬화**: 에이전트 실행을 중단·재개·재시도할 수 있도록 상태를 JSON 등으로 저장한다. 사람 승인 대기, 장애 후 재시작, 디버깅을 위한 재현이 모두 여기에 의존한다.

## 5. 실패 모드와 복구

에이전트는 일반 파이프라인보다 실패 방식이 다양하다. 대표적인 실패와 대응은 다음과 같다.

| 실패 모드 | 증상 | 대응 |
| --- | --- | --- |
| **무한 루프** | 같은 도구를 같은 인자로 반복 호출, 계획을 반복 수정 | 최대 반복 횟수, 동일 호출 감지 시 강제 종료, 반복 시 "다른 접근을 시도하라" 지시 주입 |
| **도구 오류 오해석** | 도구가 오류를 반환했는데 성공으로 간주하거나, 빈 결과를 "데이터 없음"으로 단정 | 오류 메시지를 명확하고 행동 가능하게 작성("customer_id 형식 오류: 8자리 숫자여야 함"), 성공/실패를 구조화 필드로 명시 |
| **잘못된 인자** | 존재하지 않는 ID, 형식 오류, 범위 밖 값 | 스키마 검증 실패 시 오류를 모델에 반환해 스스로 고치게 함(1~2회), 그 이상은 사용자에게 확인 |
| **환각된 도구 호출** | 정의되지 않은 도구 이름, 존재하지 않는 매개변수 | 게이트에서 거부하고 사용 가능한 도구 목록을 다시 제시 |
| **조기 종료** | 작업이 끝나지 않았는데 완료 선언 | 완료 조건을 체크리스트로 명시, 검토자 단계에서 확인 |
| **범위 이탈** | 요청하지 않은 파일 수정, 불필요한 외부 호출 | 도구 권한 최소화, 변경 대상 화이트리스트, 사람 승인 |
| **부분 실패 후 상태 불일치** | 5단계 중 3단계에서 실패해 일부만 반영됨 | 도구를 멱등(idempotent)하게 설계, 보상 트랜잭션(되돌리기) 도구 제공, 실행 전 dry-run |

재시도 정책은 계층별로 나눈다. 네트워크 등 일시적 도구 오류는 코드에서 지수 백오프로 재시도하고, 모델의 판단 오류는 오류 내용을 모델에 돌려주어 수정 기회를 준 뒤, 그래도 실패하면 사람에게 넘긴다. 모든 실패는 트레이스에 남겨 사후 분석과 평가 세트 보강에 사용한다.

## 6. 비용과 지연 통제

에이전트는 호출 횟수를 모델이 결정하므로 비용이 요청마다 크게 다르고, 상한이 없으면 예측할 수 없다.

- **예산 상한**: 요청당 최대 도구 호출 횟수, 최대 토큰 수, 최대 실행 시간을 설정하고 도달 시 "현재까지의 결과와 미완료 사항"을 정리해 반환한다. 아무 것도 반환하지 않는 실패보다 낫다.
- **모델 계층화**: 라우팅·단순 추출·형식 변환은 소형 모델, 계획·복잡한 추론은 대형 모델을 사용한다. 전체 호출의 상당수가 소형 모델로 처리 가능한 경우가 많다.
- **병렬 도구 호출**: 서로 독립적인 도구 호출(여러 문서 조회, 여러 API 질의)은 한 스텝에서 병렬 실행한다. 최신 모델은 한 응답에서 여러 도구 호출을 동시에 요청할 수 있다.
- **결과 캐싱**: 동일한 도구 호출 결과와 프리픽스 KV 캐시를 재사용한다.
- **스트리밍과 진행 표시**: 에이전트 실행은 수십 초 이상 걸릴 수 있다. 중간 상태("주문 내역 조회 중 → 환불 정책 확인 중")를 사용자에게 스트리밍하면 체감 지연이 크게 줄어든다.
- **비용 관측**: 요청별 토큰·호출 횟수·비용을 트레이스에 기록하고, 요청당 비용 분포(특히 p99)를 대시보드로 감시한다. 책 14장의 비용 관리 원칙을 요청 단위로 적용하는 것이다. 트레이싱과 운영 지표 설계는 [에이전트 관측성과 운영(AgentOps)](./agent-observability-operations.md)에서 다룬다.

<br>

## 7. 보안과 평가

에이전트는 도구를 실행하므로 [프롬프트 인젠션과 가드레일 설계](./prompt-injection-guardrails.md)에서 다룬 위협이 실제 행동으로 이어진다. 특히 다음을 반드시 적용한다.

- 도구 결과는 신뢰할 수 없는 데이터로 취급하고, 그 안의 지시를 따르지 않도록 시스템 프롬프트에 명시한다.
- 파괴적·외부 전송 행동은 사람 승인을 거치며, 승인 화면에는 실제 실행될 인자를 표시한다.
- 도구 권한은 에이전트 인스턴스별로 최소화하고, 사용자 권한을 넘어서는 행동이 불가능하도록 도구 계층에서 인가를 검사한다.

평가는 최종 응답뿐 아니라 **경로(trajectory)** 를 본다. 올바른 도구를 선택했는가, 불필요한 호출이 없었는가, 실패 시 적절히 복구했는가, 예산 안에서 끝났는가를 평가 항목에 포함한다. 평가 세트에는 정상 과제뿐 아니라 도구 오류 주입, 인젠션이 포함된 도구 결과, 모호한 요구사항 같은 시나리오를 넣어 실패 대응을 검증한다. 하네스 구축 방법은 [RAG·LLM 평가 데이터세트 구축과 오프라인 평가 하네스](./llm-evaluation-harness.md)를 따른다.

## 8. 프레임워크 선택

| 구분 | 예 | 특징 |
| --- | --- | --- |
| **모델 제공사 SDK의 도구 호출** | OpenAI·Anthropic·Gemini API의 function/tool calling | 가장 단순하고 의존성이 적음. 루프·상태 관리는 직접 구현 |
| **그래프 기반 오케스트레이션** | LangGraph, Pydantic AI | 상태 머신으로 흐름을 명시, 체크포인트·사람 개입 지원. 예측 가능성 높음 |
| **다중 에이전트 프레임워크** | AutoGen, CrewAI, OpenAI Agents SDK | 역할 기반 에이전트 협업 추상화. 편리하지만 내부 프롬프트·비용 통제가 어려울 수 있음 |
| **도구 연결 표준** | MCP | 도구 서버를 표준화해 재사용. 오케스트레이션 자체는 제공하지 않음 |

초기에는 제공사 SDK와 수십 줄의 루프로 시작해 요구사항을 파악한 뒤, 상태 관리·사람 개입·재시작이 필요해지는 시점에 그래프 기반 프레임워크로 옮기는 경로가 무난하다. 프레임워크가 숨기는 프롬프트와 호출 횟수는 반드시 트레이스로 확인해야 한다.

<br>
<br>

LLM 에이전트 설계의 요체는 **모델에게 판단을 맡기는 범위를 의도적으로 정하고, 그 범위 밖은 코드로 강제하는 것**이다. 자율성은 도구 설명·권한·예산·종료 조건이라는 울타리 안에서만 유용하며, 울타리가 없는 에이전트는 데모에서는 인상적이지만 운영에서는 예측 불가능한 비용과 위험을 낳는다. 체인으로 충분한 문제를 에이전트로 풀지 않는 절제가 가장 중요한 설계 결정이다.
