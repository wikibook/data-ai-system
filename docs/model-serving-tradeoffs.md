# 모델 서빙 시 트레이드오프 고려사항

머신러닝·딥러닝 모델을 실제 서비스 환경에서 제공하는 과정은 단순한 배포 이상을 의미한다. 모델 서빙(model serving)은 비용, 응답 시간, 정확도, 실시간성이라는 상충되는 요소들을 동시에 다루어야 하는 작업이다.

한 가지 요소를 강화하면 다른 요소가 저하되므로, `트레이드오프(trade-off)`를 어떻게 균형 있게 맞추는가가 핵심이다. 이 장에서는 모델 서빙 시 반드시 고려해야 할 주요 트레이드오프와, 이를 완화하기 위한 보완 전략을 정리한다.

<br>

## 1. 비용 vs 성능

비용을 낮추면 성능은 자연스럽게 떨어진다. 예를 들어, CPU 중심의 추론 인프라는 GPU 대비 저렴하지만, 응답 속도가 느리고 정확도 높은 대규모 모델 활용이 어렵다. 이 경우 다음과 같은 현상이 발생한다.

**비용 절감 우선 시**
- 작은 인스턴스나 CPU 기반 서빙으로 전환 → `응답 시간 증가`
- 모델 경량화(Quantization, Distillation) → `정확도 하락`

**성능 보장 우선 시**
- 고성능 GPU/TPU 사용, 대규모 클러스터 확장 → `비용 급증`

이처럼 비용과 성능은 서로를 끌어내리는 힘으로 작용한다. 서비스 환경에 따라 어느 쪽을 우선할지는 달라지지만, 단순히 한쪽을 희생하는 방식으로는 장기적인 운영이 어렵다. 특히 사용자 경험을 해치지 않으면서도 예산 제약을 지키려면, 비용 증가 없이 성능 저하를 완화하는 전략이 필요하다. 이러한 문제를 완화하기 위해 적용할 수 있는 방법은 다음과 같다.


- **모델 최적화 기법 활용**:
    - Quantization, Pruning, Distillation을 통해 모델 크기를 줄이고 추론 속도를 높인다.
    - Distillation을 적용하면 대형 모델의 성능을 유지하면서 경량 모델로 서빙할 수 있다.

- **추론 엔진 도입**:
    - ONNX Runtime, TensorRT와 같은 고성능 추론 엔진을 사용하여 동일한 하드웨어에서 성능을 개선한다.
    - CPU 환경에서도 효율이 높아져 비용 대비 성능 비율을 끌어올릴 수 있다.

- **멀티 모델 전략**:
    - 요청의 중요도에 따라 서로 다른 모델을 선택한다.
    - 예를 들어, 검색이나 추천에서는 실시간 응답이 필요한 경우 경량 모델을 사용하고, 정밀한 결과가 필요한 경우 대형 모델을 비동기적으로 호출한다.

- **캐싱(cache) 및 사전 연산**:
    - 반복적으로 발생하는 요청 결과를 캐싱하여 비용이 큰 연산을 최소화한다.
    - 실시간성이 덜 중요한 영역은 사전 계산(Pre-computation)으로 전환해 GPU 사용량을 줄인다.

<br>

## 2. 응답 시간 vs 정확도

응답 시간을 줄이려면 작은 모델을 사용하거나 입력 피처를 단순화하는 방식이 필요하다. 그러나 이 경우 모델이 포착할 수 있는 정보가 제한되어 정확도가 떨어질 수 있다. 반대로, 정확도를 높이기 위해 대규모 모델이나 복잡한 전처리를 적용하면 계산량이 증가하여 응답 시간이 길어진다.

**응답 시간 단축 우선 시**

- 작은 모델 또는 단순화된 피처 사용 → `정확도 저하`
- 배치 크기 최소화 → `자원 활용 효율 저하`

**정확도 보장 우선 시**

- 대규모 모델 또는 앙상블 사용 → `응답 지연 증가`
- 복잡한 전처리·후처리 적용 → `추론 파이프라인 지연`

이처럼 응답 속도와 정확도는 서비스 특성에 따라 상반된 요구를 가진다. 즉각적인 피드백이 중요한 서비스에서는 빠른 응답이, 정밀성이 중요한 서비스에서는 정확도가 우선된다. 하지만 어느 한쪽을 극단적으로 선택하면 사용자 경험이 크게 훼손되거나 비용이 과도하게 늘어날 수 있다. 따라서 정확도를 희생하지 않으면서도 응답 시간을 줄이는 절충적 접근이 필요하다.

**보완 전략**

- **캐싱(cache)**: 동일·유사 요청의 결과를 저장하여 반복 연산을 줄인다.
- **하이브리드 모델 구조**: 1차로 경량 모델이 후보를 필터링하고, 2차로 대형 모델이 정밀 추론한다.
- **비동기 재평가(Re-ranking)**: 우선 빠른 모델로 응답을 제공한 뒤, 시간이 허용되는 범위에서 후속적으로 랭킹을 조정한다.

<br>

## 3. 실시간성 vs 비용·정확도

실시간성을 보장하기 위해서는 항상 GPU를 대기 상태로 유지하거나, 빠른 응답을 위해 사전 계산된 결과를 활용해야 한다. 그러나 이런 접근은 비용이 크게 증가하거나 최신 데이터를 즉각 반영하기 어렵다는 단점이 있다.

**실시간성 보장 우선 시**

- GPU 상시 구동 → `운영 비용 증가`
- 사전 계산된 결과 활용 → `최신성 저하`

**비용·정확도 보장 우선 시**

- GPU 자원 최소화 → `지연 발생`
- 정확도 높은 모델 활용 → `실시간 응답 어려움`

실시간성과 비용·정확도는 서비스 환경에 따라 우선순위가 다르다. 금융 거래나 온라인 광고처럼 지연에 민감한 환경에서는 실시간성이 필수지만, 데이터 분석이나 보고서 생성처럼 지연이 허용되는 환경에서는 정확도와 비용 효율이 더 중요하다. 따라서 실시간성을 유지하면서도 불필요한 비용과 정확도 저하를 최소화하는 균형 전략이 요구된다.

**보완 전략**

- **오토스케일링(auto-scaling)**: 트래픽 패턴에 따라 GPU/TPU 인스턴스를 자동으로 증감시켜 비용을 줄인다.
- **스트리밍 파이프라인**: Kafka/Kinesis 기반으로 데이터 스트림을 처리하여 최신성을 확보한다.
- **짧은 TTL 캐싱**: 캐시를 활용하되 TTL을 짧게 설정하여 최신 데이터를 주기적으로 반영한다.

<br>

## 4. 처리량 vs 지연 시간

대규모 요청을 효율적으로 처리하려면 배치 단위로 묶어 처리하는 것이 유리하다. 하지만 이 경우 개별 요청의 지연 시간이 늘어난다. 반대로 요청 단위로 처리하면 응답은 빨라지지만 전체 처리 효율은 떨어지고 자원 낭비가 발생할 수 있다.

**처리량 극대화 우선 시**

- 대규모 배치 처리 → `개별 응답 지연 증가`
- 자원 효율성은 높지만 실시간 응답에는 부적합

**지연 시간 단축 우선 시**

- 청크 단위 추론 처리 → `처리량 감소`
- 자원 활용 효율 저하

처리량과 지연 시간은 서로 대립하는 성격을 가진다. 대규모 사용자 요청을 동시에 처리해야 하는 환경에서는 처리량이 중요하지만, 사용자 개별 경험이 중요한 환경에서는 짧은 지연 시간이 더 요구된다. 결국 상황에 따라 두 요소의 균형점을 찾고, 운영 정책에 따라 동적으로 조정 가능한 구조를 마련하는 것이 바람직하다.

**보완 전략**

- **마이크로단위 배치**: 대규모 배치 대신 소규모 묶음 단위로 처리해 효율과 응답 속도를 절충한다.

- **동적 배치 크기 조정**: 트래픽이 몰릴 때는 배치 크기를 키우고, 한산할 때는 줄여 지연을 최소화한다.

- **멀티 인스턴스 분리 운영**: 저지연 응답이 필요한 서비스와 대량 처리 중심 서비스에 각각 다른 인스턴스를 배치한다.


<br>

## 간략 요약

| 우선순위 | 얻는 점 | 희생되는 점 |
| --- | --- | --- |
| **비용 절감** | 인프라 비용 ↓ | 응답 시간 ↑, 정확도 ↓ |
| **응답 시간 단축** | 빠른 사용자 경험 | 정확도 ↓, 비용 ↑ |
| **정확도 극대화** | 모델 품질 ↑ | 응답 시간 ↑, 비용 ↑ |
| **실시간성 보장** | 실시간 서비스 가능 | 비용 ↑, 정확도 ↓ |
| **처리량 극대화** | 효율적 자원 활용 | 개별 응답 지연 ↑ |

결국 서비스의 성격에 따라 우선순위를 명확히 설정해야 한다. 다음은 대표적인 사례다.

- **광고/추천 서비스**: 응답 시간·실시간성 > 정확도
- **의료/금융 서비스**: 정확도 > 응답 시간·비용
- **대규모 사용자 서비스(검색, 쇼핑)**: 응답 시간 + 비용 균형
- **연구·실험 환경**: 정확도 > 비용·응답 시간
