# MCP 서버 설계와 운영 실무

책 12.3.4는 모델 컨텍스트 프로토콜(Model Context Protocol, MCP)을 LLM과 외부 도구·데이터를 연결하는 표준으로 소개했다. 그 이후 MCP는 주요 모델 제공사와 에이전트 프레임워크, 개발 도구가 공통으로 채택한 사실상의 표준이 되었고, 데이터 팀에게는 새로운 업무가 생겼다. 사내 데이터 웨어하우스, 피처 스토어, 실험 플랫폼, 모델 레지스트리를 **에이전트가 안전하게 쓸 수 있는 형태로 노출하는 일**이다. 이 문서는 MCP 서버를 설계·구현·배포·운영할 때의 실무 고려사항을 정리한다.

MCP 서버 위에서 동작하는 에이전트 설계는 [LLM 에이전트와 도구 호출 아키텍처](./llm-agent-architecture.md)에서, 도구 호출의 보안은 [프롬프트 인젠션과 가드레일 설계](./prompt-injection-guardrails.md)에서 다룬다.

<br>

## 1. MCP가 해결하는 문제

MCP 이전에는 도구 연동이 "모델 × 도구" 조합마다 개별 구현이었다. OpenAI 함수 호출용 스키마, LangChain 도구 클래스, 자체 에이전트용 어댑터를 같은 사내 API에 대해 따로 만들어야 했다. MCP는 이를 **호스트(에이전트 애플리케이션) – 클라이언트 – 서버(도구 제공자)** 구조로 분리한다.

```
[호스트: 에이전트 앱 / IDE / 챗 클라이언트]
   │  MCP 클라이언트 (프로토콜 처리)
   │
   ├──▶ [MCP 서버 A: 데이터 웨어하우스]  ─ 도구: run_query, list_tables, describe_table
   ├──▶ [MCP 서버 B: 피처 스토어]       ─ 도구: get_features, list_feature_views
   └──▶ [MCP 서버 C: 실험 플랫폼]       ─ 도구: get_experiment, compare_runs
```

서버는 한 번 만들면 MCP를 지원하는 모든 호스트(Claude, ChatGPT, Cursor, 사내 에이전트 등)에서 재사용된다. 데이터 팀 관점에서 MCP 서버는 **"에이전트용 API 게이트웨이"** 다. 책 7.1.4에서 다룬 API 게이트웨이가 사람이 만든 클라이언트를 위한 것이라면, MCP 서버는 모델이 클라이언트인 경우를 위한 것이다.

**MCP가 제공하는 세 가지 기본 요소**

| 요소 | 방향 | 용도 | 예 |
| --- | --- | --- | --- |
| **Tools** | 모델이 호출 | 행동·조회 | `run_query(sql)`, `create_ticket(title, body)` |
| **Resources** | 호스트가 읽어 컨텍스트에 주입 | 참조 자료 | 테이블 스키마 문서, 지표 정의서 |
| **Prompts** | 사용자가 선택 | 재사용 가능한 프롬프트 템플릿 | "이 테이블의 데이터 품질 점검 절차" |

대부분의 서버는 Tools만 구현하지만, 스키마·지표 정의 같은 참조 자료는 Resources로 노출하는 편이 도구 결과로 매번 넘기는 것보다 컨텍스트 효율이 좋다.

<br>

## 2. 도구 설계: 모델이 읽는 API

MCP 서버 설계의 90%는 도구 설계다. 사람이 쓰는 API와 다른 점은 **소비자가 문서를 읽고 판단하는 모델**이라는 것이다.

### 2.1 도구의 크기와 수

- **작업 단위로 묶는다**: REST 엔드포인트를 1:1로 노출하면 모델이 5~6번의 호출을 조합해야 하는 일이 생긴다. "주문 조회 → 상품 조회 → 재고 조회"를 모델이 하게 하지 말고 `get_order_with_items(order_id)` 하나로 만든다. 사람 개발자에게는 과도한 결합이지만, 모델에게는 오류 가능성을 줄이는 설계다.
- **10~20개 이내**: 도구가 많으면 선택 정확도가 떨어지고 스키마가 컨텍스트를 잠식한다. 서버 하나가 도메인 하나를 담당하게 나누고, 호스트가 필요한 서버만 연결하게 한다.
- **읽기와 쓰기를 분리한다**: `query_*`·`get_*`·`list_*`와 `create_*`·`update_*`·`delete_*`를 이름으로 구분하고, 쓰기 도구에는 `annotations.destructiveHint` 같은 메타데이터를 붙여 호스트가 승인 흐름을 걸 수 있게 한다.

### 2.2 설명 작성

도구 설명(description)은 모델이 읽는 유일한 문서다. 다음을 담는다.

```json
{
  "name": "run_query",
  "description": "분석용 웨어하우스에 읽기 전용 SQL을 실행한다. SELECT만 허용되며 결과는 최대 200행으로 잘린다. 테이블 이름이 불확실하면 먼저 list_tables 또는 describe_table을 호출한다. 집계가 필요한 경우 SQL에서 처리하고 원시 행을 대량으로 가져오지 않는다. 실행 시간 상한은 30초다.",
  "inputSchema": {
    "type": "object",
    "properties": {
      "sql": {"type": "string", "description": "실행할 SELECT 문. 세미콜론 없이 단일 문장"},
      "row_limit": {"type": "integer", "default": 100, "maximum": 200}
    },
    "required": ["sql"]
  }
}
```

- 언제 쓰는지, 무엇을 반환하는지, 제약(권한·범위·크기·시간)이 무엇인지, 인접 도구와의 관계를 적는다.
- 인자 설명에는 형식과 예시를 넣는다. 열거 가능한 값은 `enum`으로 고정한다.
- 설명은 곧 프롬프트이므로 [시스템 프롬프트 템플릿](./system-prompt-template.md)의 원칙(짧고 구체적, 금지 사항 명시)이 적용된다.

### 2.3 결과 설계

- **모델이 읽기 좋은 형태**: 원시 JSON보다 마크다운 표나 핵심 필드만 담은 구조가 정확도·비용 모두에 유리하다. 쿼리 결과는 열 이름과 상위 N행, 전체 행 수, 잘렸는지 여부를 함께 반환한다.
- **크기 상한**: 도구 결과 하나가 수만 토큰이면 에이전트의 컨텍스트가 무너진다. 결과 크기를 서버에서 제한하고, 초과 시 "전체 12,340행 중 200행 반환. 집계 쿼리를 사용하라"처럼 다음 행동을 안내한다. [컨텍스트 엔지니어링](./context-engineering.md) 3.2절을 참고한다.
- **오류는 행동 가능하게**: `500 Internal Error`가 아니라 "테이블 `ordr`을 찾을 수 없음. 유사한 이름: `orders`, `order_items`"처럼 모델이 스스로 고칠 수 있는 정보를 준다. 성공/실패를 구조화 필드(`isError`)로 명시한다.
- **큰 산출물은 참조로**: 파일·이미지·대용량 결과는 저장소에 두고 URI만 반환한다. 필요하면 Resource로 노출해 호스트가 선택적으로 읽게 한다.

## 3. 전송 방식과 배포

| 전송 방식 | 동작 | 적합한 경우 |
| --- | --- | --- |
| **stdio** | 호스트가 서버 프로세스를 로컬에서 실행하고 표준 입출력으로 통신 | 개발자 개인 PC, IDE 연동, 로컬 파일 접근 |
| **Streamable HTTP** | 서버가 HTTP 엔드포인트로 동작, 원격 접속 | 팀·조직 공유 서버, 중앙 인증, 운영 환경 |

데이터 팀이 만드는 서버는 대부분 **원격(HTTP) 서버**다. 개인 PC마다 웨어하우스 자격 증명을 두는 대신, 중앙 서버가 인증·권한·감사를 한곳에서 처리한다.

**배포 구조**

```
[호스트] ──HTTPS──▶ [API 게이트웨이 / 인증 프록시]
                        │  OAuth 토큰 검증, 속도 제한, 감사 로그
                        ▼
                   [MCP 서버 (컨테이너, 수평 확장)]
                        │  사용자 신원을 다운스트림에 전달
                        ▼
                   [웨어하우스 / 피처 스토어 / 내부 API]
```

- MCP 서버는 일반 웹 서비스처럼 컨테이너로 패키징하고 Kubernetes 등에 배포한다(책 11.3). 상태를 세션 저장소로 분리하면 수평 확장이 가능하다.
- SDK는 Python(`mcp`, FastMCP), TypeScript(`@modelcontextprotocol/sdk`)가 공식이며, 도구 함수에 데코레이터를 붙이는 수준으로 서버를 만들 수 있다. 복잡도는 프로토콜이 아니라 인증과 권한에 있다.

<br>

## 4. 인증과 권한

가장 중요한 원칙은 **에이전트가 사용자 권한을 넘어서지 못하게 하는 것**이다. 서버가 하나의 강력한 서비스 계정으로 웨어하우스에 접근하면, 어떤 사용자의 에이전트든 그 계정 권한으로 모든 데이터를 읽을 수 있다.

- **사용자 신원 전달(on-behalf-of)**: MCP 사양은 OAuth 2.1 기반 인증을 정의한다. 호스트가 사용자를 인증해 토큰을 받고, 서버는 토큰의 신원으로 다운스트림에 접근한다. 웨어하우스의 행 수준 보안·컬럼 마스킹이 그대로 적용된다.
- **도구별 스코프**: 읽기 도구와 쓰기 도구에 서로 다른 OAuth 스코프를 요구한다. 쓰기 스코프는 명시적 동의를 거친 사용자에게만 발급한다.
- **서비스 계정은 최소 권한**: 사용자 신원 전달이 불가능한 레거시 시스템에는 읽기 전용·특정 스키마 한정 서비스 계정을 쓰고, 서버 계층에서 사용자별 접근 제어를 추가로 구현한다.
- **비밀 정보 격리**: 자격 증명은 서버 환경(시크릿 매니저)에만 있고, 도구 결과나 오류 메시지에 절대 노출되지 않게 한다. 연결 문자열이 오류 메시지에 찍히는 사고가 흔하다.

**쓰기 도구의 안전장치**

- 파괴적 도구(`delete_*`, `update_*`, 외부 발송)는 `destructiveHint`를 표시하고, 호스트가 사용자 승인을 요구하도록 한다. 서버는 호스트의 승인 흐름을 신뢰하지 말고 자체적으로도 확인 토큰이나 dry-run 모드를 제공한다.
- 멱등성을 보장한다. 같은 요청이 두 번 와도 결과가 같아야 에이전트의 재시도가 안전하다.
- 쓰기 결과는 되돌릴 수 있게 설계한다(소프트 삭제, 변경 이력).

## 5. 운영

**관측**

- 모든 도구 호출을 사용자·호스트·도구·인자 요약·결과 크기·지연·성공 여부와 함께 기록한다. 이 로그는 감사 자료이자, 어떤 도구가 실제로 쓰이는지 파악하는 제품 데이터다.
- 지표: 도구별 호출 수·오류율·p95 지연, 결과 크기 분포, 잘림(truncation) 발생 비율, 인증 실패 수. 잘림이 잦은 도구는 설계를 다시 본다.
- 트레이스 ID를 호스트에서 서버로 전달받아 에이전트의 전체 경로와 연결한다. [에이전트 관측성과 운영](./agent-observability-operations.md)을 참고한다.

**속도·비용 제한**

- 사용자별·도구별 호출 한도와 쿼리 비용 상한(스캔 바이트, 실행 시간)을 둔다. 에이전트는 사람보다 훨씬 빠르게 반복 호출하므로, 사람 기준 한도는 쉽게 뚫린다.
- 웨어하우스 비용은 별도 웨어하우스·큐·태그로 격리해 에이전트 트래픽의 비용을 분리 측정한다(책 14.3).

**버전 관리와 호환성**

- 도구 이름·인자 스키마 변경은 API 파괴적 변경과 같다. 인자 추가는 선택(optional)으로, 이름 변경은 새 도구 추가 후 구 도구 폐기 공지로 처리한다. [데이터 계약과 스키마 진화](./data-contracts-schema-evolution.md)의 확장-축소 패턴이 그대로 적용된다.
- 도구 설명 변경은 스키마 변경이 아니지만 모델의 행동을 바꾼다. 설명 변경도 리뷰와 평가를 거친다.
- 사내 MCP 레지스트리(서버 목록, 담당 팀, 도구 목록, 스코프)를 두어 발견 가능성과 소유권을 명확히 한다.

**평가**

MCP 서버는 코드가 맞아도 모델이 잘못 쓰면 실패한다. 대표 질의 수십 개로 "모델이 올바른 도구를 올바른 인자로 호출하는가"를 측정하는 평가 세트를 만들고, 도구 설명이나 스키마를 바꿀 때마다 실행한다. 방법은 [RAG·LLM 평가 데이터세트 구축과 오프라인 평가 하네스](./llm-evaluation-harness.md)를 따른다.

## 6. 데이터 팀의 대표 서버 패턴

| 서버 | 도구 예 | 설계 포인트 |
| --- | --- | --- |
| **웨어하우스 질의** | `list_tables`, `describe_table`, `run_query`, `explain_query` | 읽기 전용 강제, 행·비용 상한, 시맨틱 레이어 경유([텍스트-투-SQL과 시맨틱 레이어](./text-to-sql-semantic-layer.md)) |
| **지표·시맨틱 레이어** | `list_metrics`, `query_metric(metric, dims, filters)` | SQL 대신 지표 이름으로 질의해 정의 불일치 제거 |
| **피처 스토어** | `list_feature_views`, `get_online_features`, `get_feature_stats` | 온라인/오프라인 구분, PII 피처 마스킹 |
| **실험·모델 레지스트리** | `list_experiments`, `compare_runs`, `get_model_card` | 읽기 중심, 모델 승격은 승인 필요 쓰기 도구 |
| **데이터 카탈로그** | `search_datasets`, `get_lineage`, `get_owner` | Resources로 문서 노출, 검색 결과 크기 제한 |
| **파이프라인 운영** | `get_dag_status`, `get_failed_tasks`, `trigger_backfill` | 트리거는 dry-run + 승인, 로그는 요약 후 반환 |

<br>
<br>

MCP 서버를 만드는 일은 기술적으로는 간단하다. 어려운 것은 "모델이라는 새로운 사용자"를 위해 API를 다시 생각하는 일이다. 사람 개발자를 위한 API가 유연성과 조합 가능성을 중시했다면, 모델을 위한 API는 **오해할 여지가 없는 설명, 예측 가능한 결과 크기, 권한을 넘지 못하는 구조**를 중시한다. 이 차이를 이해한 팀이 만든 MCP 서버는 에이전트의 정확도를 결정하는 가장 큰 변수가 된다.
